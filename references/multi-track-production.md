# 双轨/多轨净新建与教学代码生产级门禁（Multi-Track Production）

本指南规范两类易踩坑场景：**①从单一源头派生第二/第三技术栈时的双轨/多轨净新建**；
**②教学代码作为学员可复现交付物时的生产级质量门禁**。
两者都来自真实生产教训（V4 实战课 5-8 双轨新建：TS/Java 两套独立课程从单一 Java 源头净新建，
共享"评测集/指标口径/环境变量契约/术语映射表"）。

> **适用范围**：实战课·基础/实战、实战课·应用架构。
>
> **术语澄清**：本指南的「双轨/多轨」指**技术栈平行版本**（TS/Java 等）；与 `phase-2-cases.md` 的「双轨并行规则」（经验线 + 事实线两条证据线）不是一回事，加载与阅读时勿混用。

---

## 1. 双轨净新建 ≠ 多版本对齐

`phase-4-sync.md` 的 L0-L4 面向**已存在**的平行版本做**对齐**；
而"双轨净新建"（如 V3 只有 Java 版、无 TS 版）是从**单一源头**派生第二轨，
两者流程完全不同，**不能只复用 phase-4 的对齐逻辑**。

净新建的关键路径是"**契约映射表先行 → 反向派生第二轨**"。

### 1.1 前置：产出《技术栈A↔B 术语与模块映射表》（内部契约）

派生第二轨之前，必须先产出内部契约文档，存入 `.course/{task_name}/phase-3/`：

| 契约维度 | 内容 | 举例 |
|:---|:---|:---|
| **术语对照** | 同一概念在两个技术栈的术语映射 | Plan-Execute 双阶段：TS 版 `planner+executor` ↔ Java 版 `plan+executor` |
| **模块对照** | 逐模块列出两端落点 | 三域概念在两端各落在哪个包/模块 |
| **环境变量契约** | 两端 `.env.example` 必须覆盖一致的变量 | `OPENAI_API_KEY`、`MODEL_NAME` 等 |
| **未决清单** | 无法一一对应的项 | 需人工决策，不强行 1:1 映射 |

> 契约是**内部**产物，仅用于讲师侧派生辅导，**不得**进入学员可交付物（见 §3）。

### 1.2 逐课反向派生

- 以源头版本为主链，按映射表逐课派生第二轨；每课派生后过一遍 phase-4 的 L0 独立红线（见 §3）。
- 派生不等于翻译：第二轨应写"该技术栈最地道的实现"，禁止类名/方法级 1:1 翻译式映射（与 phase-4 L4 核心原则一致）。
- 契约优先：若两端无法一一对应，回到映射表更新未决清单并记入变更理由，而非强行对齐。

## 2. 教学代码生产级门禁

教学代码是学员的**可复现交付物**，审查不能停留在文档级静态视角，必须上升到"能真实跑"。

### 2.1 可编译、可运行 + 可复现环境

- [ ] 代码必须可真实编译/运行，不能只在文档里"看似正确"
- [ ] 必须写明可复现运行环境：JDK / Node 等版本号
  - 教训：JDK 26 导致 Mockito 无法插桩——运行环境与工具链版本必须实测
- [ ] README、`.env.example` 与实际执行环境一致

### 2.2 评测指标：基线对照 + 回退红线

- [ ] 评测指标须有**基线对照**（改造前 vs 改造后），不能只给绝对值
- [ ] 必须设**回退红线**并写入课程文档，例如：`overall_pass_rate ≥ 90%`、`P95 ≤ 上限值`
- [ ] 红线不达标 → 该实现不得作为课程交付形态

### 2.3 量化数字必须实测后写入

- [ ] 课程里所有量化数字（性能/指标/耗时）必须先**实测**再写入文本
- [ ] **依赖排序：评测在写作前**——先跑出数据，再据此写正文，禁止先写再补数据
- [ ] 引用数据的来源、发布时间可查证

### 2.4 端到端工业落地验收（应用架构课必检）

应用架构课的教学代码是**以工业项目落地标准驱动的生产级交付物**，而非仅为完成课程演示的脚手架。验收以**主要用户动线端到端跑通 + 无明显体验问题 + 评测指标达标**三者同时满足为前提，才能作为课程交付形态：

- [ ] **主要用户动线端到端跑通**：核心使用流程端到端真实跑通（非仅评测集单点调用），覆盖学员实际会操作的主链路，无中途卡死/报错中断
- [ ] **无明显体验问题**：运行观测无阻断性体验缺陷（响应不可用、数据错乱、越权可见、错误信息裸奔等）
- [ ] **评测指标达标**：评测指标达到设计目标（基线对照 + 回退红线通过）

> 禁止"演示可跑、指标不达标"的双轨验收；教学脚手架必须**透明演化**为生产级交付物并过评测，不得保留为可丢弃的 demo。

## 3. 两条红线分离：学员交付物零交叉 vs 讲师侧对齐审计

- [ ] phase-4 L0 的"零跨版本对比"是**学员交付物**红线，双轨独立课程必须升级为**硬红线**：
  - [ ] 学员可交付物禁止任何"与另一技术栈对比"的内容
  - [ ] 禁止出现另一技术栈的类名 / 包名 / 配置项 / 坐标（如 TS 版不得出现 Java 类名或 Maven 坐标）
  - [ ] 红线扫描 0 命中（各版本禁用词 + 对比连词 + 他栈技术名）

讲师侧**内部**对齐记录（phase-4 `sync-record.md`）可以、也应该写两版本差异——这是给讲师派生与复查用的，
**不等于**学员交付物违规。

> 一句话：**讲师侧内部对齐记录可写差异；学员可交付物零交叉。** 两者是不同红线，
> 不要因为"内部记录写了差异"就放松交付物红线。

## 4. 演进快照（git tag / branch）

演进路线类课程若只交付最终态代码，学员无法 checkout 到每课结束态。

### 4.1 演进快照规范

- [ ] 演进路线课须配 git tag 演进快照：按课时打 tag，可逐课（`v4-java-lesson5`）或区间（`v4-java-lesson5..8`）
- [ ] tag 命名：`{课程版本}-{技术栈}-lesson{N..M}`，技术栈段如 `java` / `ts`
- [ ] 每个 tag 对应该课结束态的代码，学员 checkout 即可复现该课演示

### 4.2 README tag↔课程对照表

README 必须含一张 tag↔课程对照表：

| git tag | 对应课时 | 本课结束态说明 |
|:---|:---|:---|
| `v4-java-lesson5` | 第 5 讲 | {该讲实现到的架构档位/能力} |
| `v4-java-lesson6` | 第 6 讲 | {…} |

要求：
- 每个 tag 能对应到明确的课时与结束态说明
- 对照表须与讲义"本课实现了什么"一致（对齐 phase-4 的演进起点对齐项）

### 4.3 触发时机

- 每课收尾、进入下一课派生/开发前，先打本课结束态 tag
- 双轨净新建时，两端各打各的 tag，命名以各自技术栈段区分
