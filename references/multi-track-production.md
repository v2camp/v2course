# 双轨/多轨净新建与教学代码生产级门禁（Multi-Track Production）

本指南规范两类易踩坑场景：**①从单一源头派生第二/第三技术栈时的双轨/多轨净新建**；
**②教学代码作为学员可复现交付物时的生产级质量门禁**。
两者都来自真实生产教训（V4 实战课 5-8 双轨新建：TS/Java 两套独立课程从单一 Java 源头净新建，
共享"评测集/指标口径/环境变量契约/术语映射表"）。

> **适用范围**：实战课·基础/实战、实战课·应用架构。
>
> **术语澄清**：本指南的「双轨/多轨」指**技术栈平行版本**（TS/Java 等）；与 `phase-2-cases.md` 的「双轨并行规则」（经验线 + 事实线两条证据线）不是一回事，加载与阅读时勿混用。

## 1. 双轨净新建 ≠ 多版本对齐

`phase-4-sync.md` 的 L0-L4 面向**已存在**的平行版本做**对齐**；
而"双轨净新建"（如 V3 只有 Java 版、无 TS 版）是从**单一源头**派生第二轨，
两者流程完全不同，**不能只复用 phase-4 的对齐逻辑**。

净新建的关键路径是"**契约映射表先行 → 反向派生第二轨**"。

### 1.1 前置：产出《技术栈A↔B 术语与模块映射表》（内部契约）

派生第二轨之前，必须先产出内部契约文档，存入 `.course/{task_name}/phase-3/`：

| 契约维度 | 内容 | 举例 |
|:---|:---|:---|
| **术语对照** | 同一概念在两个技术栈的术语映射 | Plan-Execute 双阶段：TS 版 `planner+executor` ↔ Java 版 `plan+executor` |
| **模块对照** | 逐模块列出两端落点 | 三域概念在两端各落在哪个包/模块 |
| **环境变量契约** | 两端 `.env.example` 必须覆盖一致的变量 | `OPENAI_API_KEY`、`MODEL_NAME` 等 |
| **未决清单** | 无法一一对应的项 | 需人工决策，不强行 1:1 映射 |

> 契约是**内部**产物，仅用于讲师侧派生辅导，**不得**进入学员可交付物（见 §3）。

### 1.2 逐课反向派生

- 以源头版本为主链，按映射表逐课派生第二轨；每课派生后过一遍 phase-4 的 L0 独立红线（见 §3）。
- 派生不等于翻译：第二轨应写"该技术栈最地道的实现"，禁止类名/方法级 1:1 翻译式映射（与 phase-4 L4 核心原则一致）。
- 契约优先：若两端无法一一对应，回到映射表更新未决清单并记入变更理由，而非强行对齐。

## 2. 教学代码生产级门禁

教学代码是学员的**可复现交付物**，审查不能停留在文档级静态视角，必须上升到"能真实跑"。

### 2.1 可编译、可运行 + 可复现环境

- [ ] 代码必须可真实编译/运行，不能只在文档里"看似正确"
- [ ] 必须写明可复现运行环境：JDK / Node 等版本号
  - 教训：JDK 26 导致 Mockito 无法插桩——运行环境与工具链版本必须实测
- [ ] README、`.env.example` 与实际执行环境一致

### 2.2 评测指标：基线对照 + 回退红线

- [ ] 评测指标须有**基线对照**（改造前 vs 改造后），不能只给绝对值
- [ ] 必须设**回退红线**并写入课程文档，例如：`overall_pass_rate ≥ 90%`、`P95 ≤ 上限值`
- [ ] 红线不达标 → 该实现不得作为课程交付形态

### 2.3 量化数字必须实测后写入

- [ ] 课程里所有量化数字（性能/指标/耗时）必须先**实测**再写入文本
- [ ] **依赖排序：评测在写作前**——先跑出数据，再据此写正文，禁止先写再补数据
- [ ] 引用数据的来源、发布时间可查证

### 2.4 端到端工业落地验收（应用架构课必检）

应用架构课的教学代码是**以工业项目落地标准驱动的生产级交付物**，而非仅为完成课程演示的脚手架。验收以**主要用户动线端到端跑通 + 无明显体验问题 + 评测指标达标**三者同时满足为前提，才能作为课程交付形态：

- [ ] **主要用户动线端到端跑通**：核心使用流程端到端真实跑通（非仅评测集单点调用），覆盖学员实际会操作的主链路，无中途卡死/报错中断
- [ ] **无明显体验问题**：运行观测无阻断性体验缺陷（响应不可用、数据错乱、越权可见、错误信息裸奔等）
- [ ] **评测指标达标**：评测指标达到设计目标（基线对照 + 回退红线通过）

> 禁止"演示可跑、指标不达标"的双轨验收；教学脚手架必须**透明演化**为生产级交付物并过评测，不得保留为可丢弃的 demo。

### 2.5 代码对照与接线核验（动笔前与审查时各做一次）

教学代码是多轮迭代出来的，**文档里写的主链路未必是今天真正在跑的链路**。这一项检查的对象不是"代码写得好不好"，而是**文档与代码是否指向同一件事**——两个方向都要对照：

- **文档 → 代码**：文档提到的每个类/函数/常量/阈值，是否真实存在、取值是否一致；
- **代码 → 文档**：文档写成"主链路"的部件，是否真的被调用（**有没有调用点**）。

#### 起点：先证伪"它没在跑"，再分层归因

对每个可疑部件搜调用点（`grep -rn "<ClassName>" src/`），看引用是否只落在**自身文件与测试**里。确认"没人调"之后再分层——四类的处置完全不同，混为一谈会开出错的药方：

| # | 归因 | 处置 |
|:---|:---|:---|
| ① | **完全没实现**（连类都不存在） | 判据二第 2 行：接 |
| ② | **实现了但没接线**（类在、无调用点） | 判据二逐行判断该不该接 |
| ③ | **接了但被另一实现短路**（有调用点、被前置条件挡住） | 先查前置条件——要修的是闸门，不是补调用点 |
| ④ | **刻意留缝**（规范已规定由外部承担） | 判据二第 5 行：不接 |

#### 判据一：取"生效值"，不是"声明值"（四层）

| 层 | 来源 | 例 |
|:---|:---|:---|
| ① 源码常量 | `export const X = 30` | 文件里的字面量 |
| ② 配置 schema 默认 | `z.coerce.number().default(30)` | 缺省值 |
| ③ `.env` 覆盖 | `X=50` | 实际部署值 |
| ④ **运行时读取** | `Number(process.env.X ?? 2500)` | 代码自己又读了一次环境变量 |

**四层缺一层就可能判错。**实测教训：契约写 5000ms、主链路单例传 3000ms（"类默认值 ≠ 生效值"）；文档写精排超时 20s、代码默认 2000ms；候选池文档写 50、常量是 30。

#### 判据二：未接线部件要判"该不该接"，不是一律接线

| 情况 | 结论 | 必须给出的证据 |
|:---|:---|:---|
| 已有**另一种实现覆盖同一功效** | **不接** | 谁在替代、覆盖面差在哪（逐分支核对，不靠印象） |
| 该功效**当前没有实现** | **接** | 现状缺什么、接上后哪个行为/指标会变 |
| 现有替代**过于简陋、达不到设计意图** | **接**（或部分接） | 对比"设计能做什么 / 现在能做什么" |
| 与现有实现**冲突而非互补**（同一出口两套口径） | **成批做**，勿单点接 | 会破坏哪些断言/口径 + 迁移顺序 |
| 属于**刻意留缝**（映射表/规范已规定由外部承担） | **不接** | 找出那条规定的原文 |

> 一句话判据：**"已实现"从来不是"该接线"的理由——判据是有没有提供现有实现提供不了的功效。**
> 措辞也要分清：**"零引用"与"已装配但无驱动者"是两件事**——前者改动面是"新增调用点"、后者是"补一个驱动者"，报错会让改动面被误判。

#### 判据三：接线的先后顺序是契约的一部分

回程链（`after` 钩子、清理/回填类钩子）的顺序决定结果——例如"输出护栏先于缓存回填"决定缓存里存的是不是**过完护栏的最终回复**。接线后若出现两处实现写同一资源，**择一保留、另一处显式空实现**，不留双实现。

#### 判据四：先修阻塞缺陷再接线（离线探针先行）

接线前先用**离线探针**把真实输入跑一遍。实测常见阻塞：解析器吃不进"标准写法"（列表项续行的缩进判据、数组元素被无条件递归拍成 `{}`）、契约与数据不同口径（枚举大小写、`version: 1.0` 解析成数字而 schema 要字符串）、校验器自相矛盾（一边依赖某哨兵值、一边把它判为"不存在"）。

> 经验：**"已实现"与"能用"之间的距离，往往就是这几行**——真实数据一个都过不了是常态。

#### 交付物与纪律

- 一张**对照表**：条目 | 文档写的 | 代码实际/生效值 | 判定 | 依据(文件:行)；
- 一段**可复现的验证**：类型检查退出码 ＋ 测试条数（改前/改后）；
- 一处**能捕获该缺陷的测试**（写进仓库，别只留在一次性探针里）；
- **代码一改，所有写"未接线"的段落立刻过期** ⇒ 收尾必须逐处回改文档，并写清接线后的新行为。

#### 常见误判（反例）

- 看到"已实现"就接上 → 得到两套并行口径（同轮对话两处出结果）。
- 只报"零引用"、不区分"没装配"与"已装配无驱动者" → 让人误判改动面。
- 只查三层生效值、漏掉**运行时**再次读取环境变量 → 结论与真实行为相反。
- 接线后不写测试 → 下次重构又把钩子摘掉，且无人发现。
- 忘了回改文档 → 教材比代码更旧，读者按文档找不到东西。

## 3. 两条红线分离：学员交付物零交叉 vs 讲师侧对齐审计

- [ ] phase-4 L0 的"零跨版本对比"是**学员交付物**红线，双轨独立课程必须升级为**硬红线**：
  - [ ] 学员可交付物禁止任何"与另一技术栈对比"的内容
  - [ ] 禁止出现另一技术栈的类名 / 包名 / 配置项 / 坐标（如 TS 版不得出现 Java 类名或 Maven 坐标）
  - [ ] 红线扫描 0 命中（各版本禁用词 + 对比连词 + 他栈技术名）

讲师侧**内部**对齐记录（phase-4 `sync-record.md`）可以、也应该写两版本差异——这是给讲师派生与复查用的，
**不等于**学员交付物违规。

> 一句话：**讲师侧内部对齐记录可写差异；学员可交付物零交叉。** 两者是不同红线，
> 不要因为"内部记录写了差异"就放松交付物红线。

## 4. 演进快照（git tag / branch）

演进路线类课程若只交付最终态代码，学员无法 checkout 到每课结束态。

### 4.1 演进快照规范

- [ ] 演进路线课须配 git tag 演进快照：按课时打 tag，可逐课（`v4-java-lesson5`）或区间（`v4-java-lesson5..8`）
- [ ] tag 命名：`{课程版本}-{技术栈}-lesson{N..M}`，技术栈段如 `java` / `ts`
- [ ] 每个 tag 对应该课结束态的代码，学员 checkout 即可复现该课演示

### 4.2 README tag↔课程对照表

README 必须含一张 tag↔课程对照表：

| git tag | 对应课时 | 本课结束态说明 |
|:---|:---|:---|
| `v4-java-lesson5` | 第 5 讲 | {该讲实现到的架构档位/能力} |
| `v4-java-lesson6` | 第 6 讲 | {…} |

要求：
- 每个 tag 能对应到明确的课时与结束态说明
- 对照表须与讲义"本课实现了什么"一致（对齐 phase-4 的演进起点对齐项）

### 4.3 触发时机

- 每课收尾、进入下一课派生/开发前，先打本课结束态 tag
- 双轨净新建时，两端各打各的 tag，命名以各自技术栈段区分

## 5. 组内混编工程组织（basic / full 双 app）

实战课组内混编（入门实战 + 应用架构，规则见 `templates.md §3.2`）时，教学工程按「单 monorepo、basic/full 双 app」组织：

```
apps/
├── lesson{N}-<域>-basic/    # 入门实战课产物：最小可跑核
└── lesson{N..M}-<域>/       # full：工业级完整版（架构课讲解对象）
packages/shared/             # 契约 / 主数据 / mock，basic 与 full 共用
```

### 5.1 basic 边界判定（五问，逐模块过）

1. **断链问**：没有它，主用户动线（输入→核心处理→可见输出）会断吗？不断 → 去 full。
2. **领域核心问**：它体现本组领域本质吗？不体现 → 去 full。
3. **可讲写问**：复杂度能在 45 分钟现场构建环节边讲边写完吗？不能 → 简化或去 full。
4. **留白问**：留给架构课能讲出"解决什么生产问题"吗？能 → 优先去 full（它是架构课素材）。
5. **独立可跑问**：砍完后仍能一条命令跑通主动线吗？不能 → 边界切错，回退。

### 5.2 basic DoD 红线（完成态验收，Phase 5 视角 H 执行）

- [ ] `install` 后**一条命令**跑通主用户动线，含 mock/降级模式，**不强依赖 LLM key**
- [ ] 核心代码 **≤ 8 个文件、≤ 500 行**（含 starter 预置在内的可讲性硬上限；其中现场写 3-4 个关键决策文件）
- [ ] 配 **3-5 条 smoke case** 手动可验（完整评测集与 CI 卡口属 full，留给架构课）
- [ ] starter 骨架含**完整类型契约 + mock 数据 + smoke 样例**；关键决策文件为带引导注释的空壳（学员跟做时现场补全）
- [ ] 课后行动清单给出「checkout starter tag 重做一遍 basic」的完整步骤
- [ ] 配 **2 张左右课后实战任务卡**（八要素见 `hands-on-lesson.md §4.2.2`），选题过「演进锚点／独立可跑／vibe 值」三问（§4.2.1）；提示词不依赖课堂上下文，验证方式如实填写
- [ ] 本课**三类保底图**（组件图 / 模式图 / 骨架图）齐备，IR 与 SVG 同目录同基名入库，无孤儿图（`diagram-integration.md §6.1`）

### 5.3 starter 与演进快照

- starter 以 git tag 交付：命名 `{课程版本}-{技术栈}-lesson{N}-starter`，学员 checkout 即得骨架并跟做，写完与仓库内 basic 完成态对照
- **starter tag 打出后须实测两项才可交付**：① 空壳态静态校验 0 错误（同 `templates.md §3.2`「空壳须类型正确」）；② 空壳态主命令确实停在预期处并报「待实现」——证明空壳真拦住了未实现路径，而非被缺依赖／缺配置提前挡在门外
- basic 完成态随课打常规演进 tag（§4.1）；**basic 定稿即冻结**，除缺陷修复不改动，full 继续演进
- full 相对 basic 的每处增强，架构课讲义必须能说出"解决什么生产问题"（对照锚点见 `architecture-course.md §3.4`）
