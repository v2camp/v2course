# 实战课·应用架构专项方法论

## 一、定位与核心差异

实战课·应用架构是实战课的一种课型，与实战课·基础/实战有本质区别：

| 维度 | 实战课·基础/实战 | **实战课·应用架构** |
|:---|:---|:---|
| 教学目标 | 技能习得、从零搭出可用系统 | **架构思维培养** |
| 代码状态 | 课上从零写 | **代码已完成（独立开发），讲义做架构解读** |
| 叙事方式 | 功能驱动：今天实现XX功能 | **问题驱动：XX模块从Baseline到生产级经历了哪些演进** |
| 量化要求 | Demo跑通、功能完整 | **每节课必须有指标提升对比表** |
| 代码讲解 | 逐模块实现 | **子系统级讲架构决策+trade-off，不逐行读代码** |
| 多版本 | 各技术栈版本并行 | **先实现主版本，其他版本视情况跟进** |

---

## 二、前置条件（开始写讲义前必须满足）

写实战课·应用架构讲义之前，以下条件**必须全部满足**，否则不得开始：

> **工业落地驱动**：实战课·应用架构的代码是**以工业项目落地标准驱动的生产级交付物**，而非仅为完成课程演示的脚手架。验收以「主要用户动线端到端跑通 + 无明显体验问题 + 评测指标达标」三者同时满足为前提，禁止"演示可跑、指标不达标"的双轨验收；教学脚手架必须透明演化为生产级交付物并过评测，不得保留为可丢弃的 demo。

1. **代码完整可运行**：目标系统可以一键启动（`docker-compose up` + 启动应用），无报错
2. **评测指标达标**：评测集上核心指标达到设计目标（参考设计文档中的验收指标表）
3. **评测脚本可用**：一键评测脚本可以运行，能输出完整的指标报告
4. **样例数据完备**：知识库、Mock数据、测试账号等全部就绪
5. **架构稳定**：代码结构不再做大的调整，允许小修小补但核心分层和模块边界必须稳定
6. **主要用户动线端到端跑通**：核心使用流程端到端真实跑通（非仅评测集单点调用），覆盖学员实际会操作的主链路，无中途卡死/报错中断
7. **无明显体验问题**：运行观测无阻断性体验缺陷（响应不可用、数据错乱、越权可见、错误信息裸奔等）
8. **指标达标方可作为交付形态**：评测指标达到设计目标且回退红线通过后，该实现方可作为课程交付形态；"演示可跑、指标不达标"不构成验收通过

如果上述条件不满足，应该等待开发完成迭代，而不是提前写讲义。

## 三、课程设计方法论

### 3.0 读者假设与正文叙述基调

**应用架构课的课程文档，目标读者是"只有文档、没开仓库的学员"**——课后在地铁上、在电脑前凭文档复习，身边没有 IDE。这条假设决定三件事：

1. **正文必须脱离仓库上下文可独立阅读**：先讲问题与方案，类名作为锚点出现（一次即可），文件路径集中放附录代码索引表，不做叙述主线；讲义版可保留路径（讲师要在 IDE 里定位），但写成代码注释或括号附注。
2. **"代码即证据"不等于"代码即叙述"**：代码引用是锚点，叙述主线是问题与方案。常量值分级——只有有信息量的数字进正文（如 2000 字符上限、28 条拦截），ID 规则这类降为一句说明。
3. **叙述质量标准**：正文须满足 `references/architecture-narrative.md` 八大病灶要求，动笔前通读 `examples/architecture-style-anchor.md` 对齐质感。演进叙事（3.2 五步法）不仅用于讲义授课节奏，也必须贯穿**课程文档正文**——"朴素做法 → 真实失败 → 方案 → 代价"，而不是只在收口给一张演进档位表。

工业案例的分工同样明确：**案例入正文（来源+关键数字，一两句话），出处留延伸阅读**——每个核心架构决策的正文至少一处工业佐证，不允许全部堆在文末。

### 3.1 单节课标准结构（90分钟）

实战课·应用架构的标准结构是：**破题→概念与决策→架构解读→量化验证→演示→收口**，区别于实战课·基础/实战的"破题→概念→编码→验证"。

| 时间段 | 环节 | 核心要求 |
|:---|:---|:---|
| 0-5min | **破题** | 用一个真实痛点场景开场：展示Baseline版本的bad case，让学员直观感受到"为什么需要调优这个模块"。不要空谈概念。 |
| 5-25min | **核心概念与架构决策** | 讲清楚这个子系统的设计决策：<br>• 为什么需要这个模块？解决什么问题？<br>• 有哪些备选方案？为什么选了当前方案？<br>• 设计的trade-off是什么？什么场景下不需要这么复杂的设计？ |
| 25-70min | **架构解读与代码映射** | 讲解子系统内部结构：<br>• 分层/模块划分（展示真实代码目录结构，不是虚构的）<br>• 核心接口与实现的设计思路<br>• 关键代码片段解读（只讲关键逻辑，不逐行读）<br>• **演进阶梯**：从最简版本开始，一步步演示每个优化点解决了什么问题 |
| 70-80min | **量化验证** | 运行评测脚本，展示指标对比表：<br>• Baseline指标<br>• 每个优化步骤后的指标变化<br>• 最终达到的指标<br>必须展示真实的评测输出，不能虚构数字。 |
| 80-85min | **端到端演示** | 运行完整系统，演示本节课模块在实际场景中的效果，对比Baseline版本的差异。 |
| 85-90min | **收口与预告** | 总结本节课的架构决策要点→预告下节课要解决什么新问题→handoff到下节课。 |

**量纲纪律（90 分钟课程 / 150 分钟内容量）**：课堂实跑 90 分钟，但内容准备须按「能支撑约 150 分钟扎实教学」做——留足深化追问、演进展开与回旋的时间余量。补量**不准凑字数、不准凑案例**，只按本课型要求补真干货：演进叙事、量化对比表、ADR/trade-off、案例入正文、术语白话。判定基准：删掉所有表格与代码后，正文仍能靠文字讲通；新增的每一行都指向「决策 / 演进 / 成本」，而不是把一句话拆成三句；新引案例须有可验证出处并即揉进正文作佐证。

### 3.2 子系统演进叙事法

每个核心模块的讲解必须采用**演进叙事法**，而不是"直接展示最终完美方案"：

```
【演进叙事五步法】

1. Baseline问题展示
   → 先展示最简版本（甚至是有缺陷的版本）
   → 用真实bad case说明"这个版本有什么问题"
   → 量化说明问题有多严重（如"Precision@5只有60%，意味着每5条结果有2条噪音"）

2. 第一次优化
   → 做了什么改动
   → 为什么这么改（不是拍脑袋，是被问题逼出来的）
   → 解决了什么问题，指标提升了多少
   → 带来了什么新问题/trade-off（没有银弹）

3. 第二次优化
   → 新问题是什么
   → 做了什么改动
   → 指标提升了多少
   → 还有什么不足

4. ...（根据需要继续迭代）

5. 最终生产级方案
   → 最终架构是什么样
   → 最终指标达到多少
   → 这个方案的适用边界是什么（什么时候不要用）
   → 真实生产中还有哪些可继续优化的方向（点到为止，不展开）
```

**关键原则**：每一步演进都要有**问题驱动**和**量化收益**，让学员感受到"架构是演进出来的，不是一开始就设计成完美形态的"。

### 3.3 架构决策讲解法（ADR轻量版）

对于每个关键架构决策，讲解时必须覆盖五个要素：

| 要素 | 说明 | 示例 |
|:---|:---|:---|
| **Context（背景）** | 面临什么问题，有什么约束 | "单路向量检索要么漏要么噪，Precision@5只有60%" |
| **Failure（失败现场）** | 不这么做会怎样——带现场感（什么时间、什么症状、谁受影响） | "大促凌晨，检索返回错表，客服 Agent 把 A 店的库存答成 B 店的，值班同学被告警叫醒" |
| **Options（备选方案）** | 考虑了哪几个方案 | "方案A：只换更好的Embedding模型；方案B：加大Top-K；方案C：多路召回+融合" |
| **Decision（决策）** | 选了哪个方案 | "选了方案C，多路召回+RRF融合" |
| **Consequences（后果）** | 选了之后带来了什么，trade-off是什么 | "Recall@20提升到90%，但检索延迟增加了100ms（并行调用可缓解），系统复杂度上升" |

**Failure 要素的写作要求**：对齐大厂复盘文体，写清"什么时候、什么症状、谁受影响"，而不是一句"会出问题"。反例："不做会有安全风险"（空）；正例："一句话注入就能把整库 SELECT\* 拖出来，含手机号列"（有现场）。

**工业案例的「规模与约束」要求**：案例入正文，价值不在"某厂也这么做了"（背书），而在"它在什么规模、什么约束下被迫这么做"（可迁移的判断力）。每个案例须带三件套——**规模**（QPS/数据量/团队规模）、**约束**（什么资源受限/什么红线不能碰）、**逼出的设计**（所以才选了这条路）。缺这三件套的案例只是引用，不是论据。

## 五、量化与评测规范

### 5.1 指标对比表标准格式

每节课必须有至少一张指标对比表，格式如下：

| 阶段 | Recall@20 | Precision@5 | P95延迟 | 说明 |
|:---|:---|:---|:---|:---|
| Baseline（单路向量） | 70% | 60% | 800ms | 最简版本，只有向量检索 |
| + 查询改写+HyDE | 80% | 68% | 1.2s | 增加查询理解 |
| + 多路召回+RRF | 92% | 80% | 1.5s | 三路并行召回+融合 |
| + 级联Rerank（最终） | **95%** | **92%** | 400ms* | *缓存预热后 |

- 必须有Baseline列
- 必须有最终列
- 中间列对应每一步演进
- 最优值用**加粗**标出
- 特殊说明（如缓存、降级）用脚注说明

### 5.2 评测集要求

- 评测集作为课程核心资产，放在 `src/test/eval/eval-set.jsonl`
- 必须包含四类case：
  - 正常单轮问答/交互
  - 多轮对话/状态交互
  - 边界case（歧义、模糊提问、知识冲突）
  - 攻击case（提示注入、越权、PII泄露尝试）
- 评测脚本必须一键可运行：`./src/test/eval/run-eval.sh`

## 六、与现有Phase流程的适配

实战课·应用架构仍然遵循course-skill的6阶段流程，但各阶段有特殊要求：

### Phase 0（探索阶段）新增要求
- **代码架构探索**：必须先全面阅读代码仓库结构，画出分层架构图，列出核心模块清单
- **确认代码达标**：运行评测脚本，确认指标达到设计目标；如果未达标，反馈给开发继续迭代
- **确认模块边界**：和用户确认系列课各课时分别讲解哪些子系统，边界在哪里，避免知识点遗漏或重复
- **确认代码根目录与包前缀**：明确教学代码的根目录路径和通用包前缀（用于包路径简写）

### Phase 1（主轴阶段）新增要求
- **系列课整体主轴**：不是若干节独立的课，而是一个完整系统的多个切面——讲完拼起来是一套完整的生产级系统
- **子系统演进线**：每个子系统的演进阶梯必须提前规划好，Baseline→优化1→优化2→最终，每一步都要有量化指标
- **跨课时handoff**：前一模块结束时后续模块能用上已讲解模块的数据/能力；最后一个模块的护栏/缓存/可观测包裹前面所有模块

### Phase 2（证据系统）新增要求
- **代码即证据**：主要证据来自真实代码和评测结果，工业案例作为辅助佐证（不是主要证据来源）
- **评测数据准备**：提前运行评测，记录Baseline和各阶段的指标数据，作为讲义中的量化证据
- **架构决策记录**：对于每个关键决策，记录Context/Options/Decision/Consequences，可以从代码commit历史、开发过程记录中提炼
- agent-reach仍然需要使用：用于补充工业界最佳实践对比、关联阅读材料，但不是为了"找案例凑数"

### Phase 3（生产阶段）新增要求
- **Read代码后再写**：写每一部分之前必须先Read对应代码文件，确认类名、方法名、路径准确
- **风格锚点先行**：动笔写正文前通读 `examples/architecture-style-anchor.md`（开场、演进叙事、语言质感三个样本），对齐"李智慧式"质感后再落笔
- **演进叙事优先**：按照"演进叙事五步法"来写，不要上来就展示最终完美代码；课程文档正文同样按演进线展开，演进不只在收口表格里
- **量化表格先行**：指标对比表是每节课的核心骨架，先把表格填好（用真实评测数据），再围绕表格展开讲解
- **代码片段精选**：只贴最关键的10-30行核心逻辑，不要大段贴代码；完整代码让学员去仓库看
- **架构决策透明**：每个关键决策都要讲"我们考虑了什么、选了什么、为什么、trade-off是什么"
- **飞书兼容代码引用**：严格遵循 `references/code-reference-feishu.md`，使用双锚点法，禁用 file:// 链接，每讲配核心代码索引表。讲义和课程文档都必须达标。
- **课程文档转换**：从讲义转换为课程文档时，代码引用（类名/路径/索引表）必须原样保留，代码讲解从口播式转为注释式，但技术准确性不得下降；同时按 §3.0 读者假设执行——正文按类名锚点引用、路径收进附录索引表。

### Phase 4（同步阶段）调整
- 实战课·应用架构**初始可只有主版本**，其他版本视后续需求开发，因此Phase 4多版本同步不做强制要求
- 如果后续开发其他版本，仍然遵循L1-L4分层同步原则，但由于是基于两套独立代码（不是翻译），更要注意L1-L2对齐

### Phase 5（审查阶段）新增检查项
除了原有视角 A-H 审查，实战课·应用架构新增：
- **代码引用准确性审查**：抽查讲义和课程文档中引用的所有类名、包路径简写是否真实存在（技术布道师负责，两份文档都要查）
- **飞书兼容性审查**：全文不得有 file:// 链接，每讲必须有核心代码索引表（表达教练负责，讲义和课程文档都要查）
- **量化数据真实性审查**：验证讲义中的指标数据是否可以通过评测脚本复现
- **演进叙事合理性审查**：每一步演进是否有对应的问题驱动和量化收益，是否存在"一步到位的过度设计"
- **架构决策完整性审查**：关键决策是否讲了trade-off，是否讲了"什么时候不需要"
- **反过度设计审查**：是否把生产级方案直接灌给学员，没有讲清楚适用边界
- **叙述质量必查项**（表达教练负责，逐段核对不得抽样）：按 `references/architecture-narrative.md` 检查病灶三（演进静态化）、四（术语无释）、五（开场没代入）、七（代码细节前置）、八（案例隔离）——这五条最直接影响学员可读性
- **两文档技术一致性**：讲义和课程文档的技术内容是否完全对齐，有没有因为文体转换引入偏差（技术布道师负责）

## 七、简历/面试表达升级

实战课·基础/实战阶段的表达是通用方法论层面的，应用架构阶段的表达应该**用真实项目数据**替换：

| 通用话术 | 升级版（用真实数据） |
|:---|:---|
| "我实现了基于RAG的企业知识库问答系统" | "我设计了内容分级+智能分片+质量校验的三层知识工程Pipeline，坏片率从30%降到5%以下，Recall直接提升12个点" |
| "通过Rerank将Precision@5从60%提升至90%" | "我设计了'查询理解→三路并行召回→RRF融合→级联Rerank'的四级检索架构，Recall@20从70%提升到95%，Precision@5从60%提升到92%，级联Rerank兼顾效果与成本——本地BGE做粗排零API成本，Cohere做精排保精度" |
