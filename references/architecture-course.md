# 实战课·应用架构专项方法论

## 一、定位与核心差异

实战课·应用架构是实战课的一种课型，与实战课·基础/实战有本质区别：

| 维度 | 实战课·基础/实战 | **实战课·应用架构** |
|:---|:---|:---|
| 教学目标 | 技能习得、从零搭出可用系统 | **架构思维培养** |
| 代码状态 | 课上从零写 | **代码已完成（独立开发），讲义做架构解读** |
| 叙事方式 | 功能驱动：今天实现XX功能 | **问题驱动：XX模块从Baseline到生产级经历了哪些演进** |
| 量化要求 | Demo跑通、功能完整 | **每节课必须有指标提升对比表** |
| 代码讲解 | 逐模块实现 | **子系统级讲架构决策+trade-off，不逐行读代码** |
| 多版本 | 各技术栈版本并行 | **先实现主版本，其他版本视情况跟进** |

---

## 二、前置条件（开始写讲义前必须满足）

写实战课·应用架构讲义之前，以下条件**必须全部满足**，否则不得开始：

1. **代码完整可运行**：目标系统可以一键启动（`docker-compose up` + 启动应用），无报错
2. **评测指标达标**：评测集上核心指标达到设计目标（参考设计文档中的验收指标表）
3. **评测脚本可用**：一键评测脚本可以运行，能输出完整的指标报告
4. **样例数据完备**：知识库、Mock数据、测试账号等全部就绪
5. **架构稳定**：代码结构不再做大的调整，允许小修小补但核心分层和模块边界必须稳定

如果上述条件不满足，应该等待开发完成迭代，而不是提前写讲义。

## 三、课程设计方法论

### 3.1 单节课标准结构（90分钟）

实战课·应用架构的标准结构是：**破题→概念与决策→架构解读→量化验证→演示→收口**，区别于实战课·基础/实战的"破题→概念→编码→验证"。

| 时间段 | 环节 | 核心要求 |
|:---|:---|:---|
| 0-5min | **破题** | 用一个真实痛点场景开场：展示Baseline版本的bad case，让学员直观感受到"为什么需要调优这个模块"。不要空谈概念。 |
| 5-25min | **核心概念与架构决策** | 讲清楚这个子系统的设计决策：<br>• 为什么需要这个模块？解决什么问题？<br>• 有哪些备选方案？为什么选了当前方案？<br>• 设计的trade-off是什么？什么场景下不需要这么复杂的设计？ |
| 25-70min | **架构解读与代码映射** | 讲解子系统内部结构：<br>• 分层/模块划分（展示真实代码目录结构，不是虚构的）<br>• 核心接口与实现的设计思路<br>• 关键代码片段解读（只讲关键逻辑，不逐行读）<br>• **演进阶梯**：从最简版本开始，一步步演示每个优化点解决了什么问题 |
| 70-80min | **量化验证** | 运行评测脚本，展示指标对比表：<br>• Baseline指标<br>• 每个优化步骤后的指标变化<br>• 最终达到的指标<br>必须展示真实的评测输出，不能虚构数字。 |
| 80-85min | **端到端演示** | 运行完整系统，演示本节课模块在实际场景中的效果，对比Baseline版本的差异。 |
| 85-90min | **收口与预告** | 总结本节课的架构决策要点→预告下节课要解决什么新问题→handoff到下节课。 |

### 3.2 子系统演进叙事法

每个核心模块的讲解必须采用**演进叙事法**，而不是"直接展示最终完美方案"：

```
【演进叙事五步法】

1. Baseline问题展示
   → 先展示最简版本（甚至是有缺陷的版本）
   → 用真实bad case说明"这个版本有什么问题"
   → 量化说明问题有多严重（如"Precision@5只有60%，意味着每5条结果有2条噪音"）

2. 第一次优化
   → 做了什么改动
   → 为什么这么改（不是拍脑袋，是被问题逼出来的）
   → 解决了什么问题，指标提升了多少
   → 带来了什么新问题/trade-off（没有银弹）

3. 第二次优化
   → 新问题是什么
   → 做了什么改动
   → 指标提升了多少
   → 还有什么不足

4. ...（根据需要继续迭代）

5. 最终生产级方案
   → 最终架构是什么样
   → 最终指标达到多少
   → 这个方案的适用边界是什么（什么时候不要用）
   → 真实生产中还有哪些可继续优化的方向（点到为止，不展开）
```

**关键原则**：每一步演进都要有**问题驱动**和**量化收益**，让学员感受到"架构是演进出来的，不是一开始就设计成完美形态的"。

### 3.3 架构决策讲解法（ADR轻量版）

对于每个关键架构决策，讲解时必须覆盖四个要素：

| 要素 | 说明 | 示例 |
|:---|:---|:---|
| **Context（背景）** | 面临什么问题，有什么约束 | "单路向量检索要么漏要么噪，Precision@5只有60%" |
| **Options（备选方案）** | 考虑了哪几个方案 | "方案A：只换更好的Embedding模型；方案B：加大Top-K；方案C：多路召回+融合" |
| **Decision（决策）** | 选了哪个方案 | "选了方案C，多路召回+RRF融合" |
| **Consequences（后果）** | 选了之后带来了什么，trade-off是什么 | "Recall@20提升到90%，但检索延迟增加了100ms（并行调用可缓解），系统复杂度上升" |

## 四、代码引用规范（飞书兼容版）

> **为什么有这一节**：应用架构课基于已有代码讲解，需要大量引用代码位置。但课程文档最终要发布到飞书文档（docs.feishu.cn），本地 `file://` 链接在飞书里全部失效变成空链。因此必须使用飞书兼容的代码引用方式。

### 4.1 核心原则：讲义是"导航地图"，不是"IDE跳转器"

学员阅读讲义的场景是**一边看飞书文档，一边在 IDE 里打开代码项目**。代码引用的目标是"告诉学员去哪里找"，而不是"点一下就能跳过去"。

因此，代码引用遵循以下原则：
1. **不使用任何本地 file:// 链接**——飞书文档中必然失效
2. **不依赖外部 GitHub 链接**——点击跳转出飞书体验差，且依赖仓库状态
3. **类名即锚点**——工程师的肌肉记忆是按类名搜索（IDE 双击 Shift / Cmd+O）
4. **路径作辅助**——提供相对路径帮助不熟悉代码结构的学员定位

### 4.2 正文引用方式：双锚点法

正文中引用代码时，使用「**类名 + 包路径简写**」双锚点：

**格式**：`` `ClassName`（`package.subpackage`）``

- 前面是类名（行内代码格式），作为主锚点——学员可以直接在 IDE 里搜类名
- 后面括号里是包路径简写（行内代码格式），作为辅助锚点——帮助定位模块位置

**示例**：

> 项目里用 `{ClassName}`（`{module.submodule}`）作为{模块功能描述}，各具体实现分别处理各自逻辑。

**首次出现 vs 后续出现**：
- **首次出现**某个类时，必须给出完整信息：类名 + 包路径简写
- **后续再次出现**同一类时，可只写类名，不用重复包路径

**包路径简写规则**：
- 从模块特征包开始，省略组织/项目通用前缀（如 `com.{company}.{project}`）
- 例如完整路径是 `com.{company}.{project}.infrastructure.{module}.{submodule}.{ClassName}`，简写为 `{module}.{submodule}`
- 简写后必须能唯一识别到包，不能歧义

### 4.3 关键代码片段展示

展示关键代码片段时，格式如下：

```java
// 文件：{path/to/ClassName}.java
public class {ClassName} {
    // 仅展示核心逻辑（10-30行）
    // 用注释标注省略部分
}
```

规则：
- 代码块上方用注释标注相对路径（从 `src/main/java/` 开始）
- 只展示核心逻辑，省略无关部分用注释说明
- 完整代码让学员去 IDE 里看，讲义不做代码搬运工

### 4.4 每讲必配：核心代码索引表

每讲末尾必须有一张「**本讲核心代码索引**」表格，集中列出本讲涉及的所有核心类。

**格式**：

| 模块 | 类名 | 相对路径 | 核心职责 |
|:---|:---|:---|:---|
| {模块A} | `{ClassA}` | `{path/to/ClassA}.java` | {一句话描述核心职责} |
| {模块B} | `{ClassB}` | `{path/to/ClassB}.java` | {一句话描述核心职责} |
| {模块C} | `{ClassC}` | `{path/to/ClassC}.java` | {一句话描述核心职责} |

**要求**：
- 至少列出本讲所有在正文中提到的类
- 按模块分组，同类模块放一起
- 相对路径从 `src/main/java/`（或对应源目录）开始
- 核心职责一句话说清，不超过20字
- 这张表是学员复习和定位代码的主入口

### 4.5 课程级前置说明

应用架构系列课的**第一节课开头**，必须在课程信息区明确标注：

```
> 教学代码根目录：`{path/to/project-root/}`
> 代码路径约定：所有相对路径均相对于 `{src/main/java/ 或对应源目录}`
> 建议学习方式：在 IDE 中打开项目，按类名搜索（Cmd+O / Shift+Shift）定位
```

### 4.6 代码引用三原则（保留并增强）

1. **先Read再引用**：引用任何类、方法、文件路径之前，必须先用Read工具读取真实文件，确认其存在和结构
2. **类名必须准确**：拼写、大小写必须与真实代码完全一致——类名是学员搜索的锚点，错了就搜不到
3. **代码片段可溯源**：展示的代码片段必须是真实代码的节选（可省略无关部分），但保留核心逻辑，不得虚构不存在的方法/类

### 4.7 代码讲解粒度

| 讲解粒度 | 适用场景 | 反模式 |
|:---|:---|:---|
| **架构级**（包/模块关系） | 讲解分层结构、模块划分 | 上来就钻进某个方法的细节 |
| **接口级**（核心接口/类） | 讲解模块边界、扩展点设计 | 纠结于private方法的实现细节 |
| **关键代码片段**（10-30行） | 讲解核心算法/逻辑（如RRF融合公式、级联Rerank逻辑） | 整页整页贴大段代码逐行念 |
| **配置级** | 讲解关键配置项（如向量数据库索引参数、模型调用阈值） | 把所有配置文件都贴一遍 |

**原则**：架构课讲的是"为什么这么设计"，不是"怎么写每一行代码"。代码已经在仓库里了，学员可以自己去看，课上只讲最关键的设计决策。

### 4.8 飞书兼容性自检清单

写完讲义后，用以下清单自检代码引用是否符合飞书兼容要求：

- [ ] 全文没有 `file://` 开头的链接
- [ ] 全文没有指向本地绝对路径的 Markdown 链接
- [ ] 所有类名用行内代码格式标注（`` `ClassName` ``）
- [ ] 每个类首次出现时带有包路径简写
- [ ] 每讲末尾有「本讲核心代码索引」表
- [ ] 索引表中的类名、路径与真实代码完全一致
- [ ] 第一节课开头有代码根目录和学习方式说明

## 五、量化与评测规范

### 5.1 指标对比表标准格式

每节课必须有至少一张指标对比表，格式如下：

| 阶段 | Recall@20 | Precision@5 | P95延迟 | 说明 |
|:---|:---|:---|:---|:---|
| Baseline（单路向量） | 70% | 60% | 800ms | 最简版本，只有向量检索 |
| + 查询改写+HyDE | 80% | 68% | 1.2s | 增加查询理解 |
| + 多路召回+RRF | 92% | 80% | 1.5s | 三路并行召回+融合 |
| + 级联Rerank（最终） | **95%** | **92%** | 400ms* | *缓存预热后 |

- 必须有Baseline列
- 必须有最终列
- 中间列对应每一步演进
- 最优值用**加粗**标出
- 特殊说明（如缓存、降级）用脚注说明

### 5.2 评测集要求

- 评测集作为课程核心资产，放在 `src/test/eval/eval-set.jsonl`
- 必须包含四类case：
  - 正常单轮问答/交互
  - 多轮对话/状态交互
  - 边界case（歧义、模糊提问、知识冲突）
  - 攻击case（提示注入、越权、PII泄露尝试）
- 评测脚本必须一键可运行：`./src/test/eval/run-eval.sh`

## 六、模块划分参考（示例）

应用架构系列课通常按**子系统/模块**切分课时，而非按知识点。以下是一个电商客服RAG系统的模块切分示例，仅作参考，实际项目应根据真实代码架构在Phase 0与用户确认：

### 模块示例1：知识供应链工程
- **聚焦子系统**：`knowledge/` 包（采集、分类、分片、质检、入库Pipeline）
- **核心问题**：RAG效果不好80%是数据问题，垃圾进垃圾出
- **演进叙事**：固定分片→标题感知分片→语义分片→父子分片→质量校验Pipeline
- **核心指标**：坏片率、入库覆盖率、分片质量对Recall的影响
- **不涉及**：检索逻辑、对话逻辑、工程化（留到后续模块）

### 模块示例2：检索引擎设计
- **聚焦子系统**：`domain/retrieval/` 包（查询理解、多路召回、融合、Rerank）
- **核心问题**：单路向量检索的天花板，怎么平衡Recall和Precision
- **演进叙事**：单路向量→查询改写+HyDE→多路召回→RRF融合→级联Rerank
- **核心指标**：Recall@20、Precision@5、MRR、检索延迟
- **不涉及**：多轮对话、工具调用、缓存护栏（留到后续模块）

### 模块示例3：对话引擎与工具调用
- **聚焦子系统**：`domain/dialogue/` + `domain/tools/` + `service/ConversationService.java`
- **核心问题**：RAG只能问答，客服需要"办事"——多轮、槽位、工具调用
- **演进叙事**：单轮RAG→意图识别→DST状态追踪→槽位填充+追问→工具网关→完整对话编排
- **核心指标**：意图识别准确率、槽位F1、任务完成率、工具调用准确率
- **架构决策点**：为什么客服场景用单Agent+状态机而不是Multi-Agent？
- **不涉及**：缓存、护栏、可观测、评测（留到后续模块）

### 模块示例4：生产级工程化与评测闭环
- **聚焦子系统**：`domain/guardrails/` + `infrastructure/cache/` + `infrastructure/llm/ModelRouter.java` + `infrastructure/observability/` + `eval/` + HITL人工介入
- **核心问题**：PoC到生产的最后一公里——安全、成本、性能、质量怎么保证
- **演进叙事**：没有护栏→五维护栏；没有缓存→三级缓存；小模型打天下→模型路由；没有评测→评测闭环；纯自动→人工兜底
- **核心指标**：P95延迟、Token成本降低率、缓存命中率、注入拦截率、Faithfulness、评测通过率
- **收尾**：整个系统整体回顾+面试/简历表达升级

## 七、与现有Phase流程的适配

实战课·应用架构仍然遵循course-skill的6阶段流程，但各阶段有特殊要求：

### Phase 0（探索阶段）新增要求
- **代码架构探索**：必须先全面阅读代码仓库结构，画出分层架构图，列出核心模块清单
- **确认代码达标**：运行评测脚本，确认指标达到设计目标；如果未达标，反馈给开发继续迭代
- **确认模块边界**：和用户确认系列课各课时分别讲解哪些子系统，边界在哪里，避免知识点遗漏或重复
- **确认代码根目录与包前缀**：明确教学代码的根目录路径和通用包前缀（用于包路径简写）

### Phase 1（主轴阶段）新增要求
- **系列课整体主轴**：不是若干节独立的课，而是一个完整系统的多个切面——讲完拼起来是一套完整的生产级系统
- **子系统演进线**：每个子系统的演进阶梯必须提前规划好，Baseline→优化1→优化2→最终，每一步都要有量化指标
- **跨课时handoff**：前一模块结束时后续模块能用上已讲解模块的数据/能力；最后一个模块的护栏/缓存/可观测包裹前面所有模块

### Phase 2（证据系统）新增要求
- **代码即证据**：主要证据来自真实代码和评测结果，工业案例作为辅助佐证（不是主要证据来源）
- **评测数据准备**：提前运行评测，记录Baseline和各阶段的指标数据，作为讲义中的量化证据
- **架构决策记录**：对于每个关键决策，记录Context/Options/Decision/Consequences，可以从代码commit历史、开发过程记录中提炼
- agent-reach仍然需要使用：用于补充工业界最佳实践对比、关联阅读材料，但不是为了"找案例凑数"

### Phase 3（生产阶段）新增要求
- **Read代码后再写**：写每一部分之前必须先Read对应代码文件，确认类名、方法名、路径准确
- **演进叙事优先**：按照"演进叙事五步法"来写，不要上来就展示最终完美代码
- **量化表格先行**：指标对比表是每节课的核心骨架，先把表格填好（用真实评测数据），再围绕表格展开讲解
- **代码片段精选**：只贴最关键的10-30行核心逻辑，不要大段贴代码；完整代码让学员去仓库看
- **架构决策透明**：每个关键决策都要讲"我们考虑了什么、选了什么、为什么、trade-off是什么"
- **飞书兼容代码引用**：严格遵循「四、代码引用规范（飞书兼容版）」，使用双锚点法，禁用 file:// 链接，每讲配核心代码索引表

### Phase 4（同步阶段）调整
- 实战课·应用架构**初始可只有主版本**，其他版本视后续需求开发，因此Phase 4多版本同步不做强制要求
- 如果后续开发其他版本，仍然遵循L1-L4分层同步原则，但由于是基于两套独立代码（不是翻译），更要注意L1-L2对齐

### Phase 5（审查阶段）新增检查项
除了原有五视角审查，实战课·应用架构新增：
- **代码引用准确性审查**：抽查讲义中引用的所有类名、包路径简写是否真实存在（技术布道师负责）
- **飞书兼容性审查**：全文不得有 file:// 链接，每讲必须有核心代码索引表（表达教练负责）
- **量化数据真实性审查**：验证讲义中的指标数据是否可以通过评测脚本复现
- **演进叙事合理性审查**：每一步演进是否有对应的问题驱动和量化收益，是否存在"一步到位的过度设计"
- **架构决策完整性审查**：关键决策是否讲了trade-off，是否讲了"什么时候不需要"
- **反过度设计审查**：是否把生产级方案直接灌给学员，没有讲清楚适用边界
