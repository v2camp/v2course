# 架构叙述方式规范 (Architecture Narrative Guide)

本规范解决架构类长文档（应用架构课课程文档、架构案例分析书等）最容易出现的**"生涩"**问题：信息全对、结构完整，但读起来像清单、像笔记，不像资深架构师在讲一个系统的故事。风格基准为李智慧《大型网站技术架构》——平实直白、业务驱动、演进视角、全局权衡。

本规范是 `architecture-case-writing.md` 的**叙述层面深挖**：
- `architecture-case-writing.md` 管结构——五段式章节怎么搭、对比表怎么写
- 本规范管落笔——句子怎么连成段、表后怎么解读、演进怎么讲出来

适用于：以架构设计为核心的长文档正文（应用架构课课程文档、架构案例分析书章节），同样作用于讲义与课程文档的叙述质量。

## 1. 八大"生涩"病灶与对策

### 病灶一：电报体——句子被压碎，停顿密

**症状**：大量"名词短语 + 破折号 + 结论"，一句话塞两个信息点，缺主语、缺因果。

- ❌ "先查数据、再查模型，是 RAG 工程第一纪律。"
- ✅ "排障要层层下钻：先怀疑数据层，排除之后才轮到模型层。因为数据层问题会'伪装'成模型层问题——你看到的现象是回答不对，根因可能是召回的数据本身错了。未排除数据层就调整提示词、更换模型，是在错误方向上投入。"

**判据**：读完一句，能否说出"谁、做了什么、为什么"。说不出的，就是电报体。

### 病灶二：清单体——列表与表格之间缺"串起来"的文字

**症状**：全文表格密排，表与表之间零文字解读；"1. 2. 3."编号列表直接排开，各自独立。

**对策**：
- 表格前：一句"这张表回答什么问题"；
- 表格后：一两句"把表里最本质的取舍串起来"，而不是直接进入下一节；
- 编号列表之间：用因果或转折连接成段，而不是各点独立成行。

- ❌ 表格 → 空行 → 下一节标题
- ✅ 表格 → "这张表的要点在'代价'行：……这也是所有类似架构的共性——收益在 A，付出在 B。"

### 病灶三：演进视角被静态表格化

**症状**：演进对比表（S0/S1/S2…）放在收口处，正文却从头到尾平铺直叙，没有"演进线"。

**对策**：每个子系统的正文，都按**"朴素做法长什么样 → 它在真实输入下怎么失败 → 本方案补上了哪一环 → 换了什么代价"**推进。演进不是只在收口给一张表，而是贯穿正文的叙述主线。

**硬约束（防"只在收口有演进"的半吊子）**：
- 正文各核心小节**必须按演进顺序组织**，每节开场第一句承接上一环的失败（用"既然/但/问题在于"等连接词），收口处的演进表只是**归档**、不是**首次呈现**。
- 反例（实测踩过的坑）：某课把演进主线表补在收口段，但正文核心小节仍按"模块A→模块B→模块C"平铺——读者在读模块A时，不知道它是"上一环失败后的解法"。演进线在收口处回头串 ≠ 在正文里向前引。

**自检（加一条）**：删掉所有演进表后，正文段落顺序本身仍能读出"朴素→失败→改进"的链条；读不出即病灶三未除。

### 病灶四：术语首现不给解释

**症状**：专业缩写、框架术语第一次出现直接使用，默认读者已懂。

**对策**：任何术语首现，用一句大白话交代"它是什么、为什么这里用"。宁可多写一句，不让读者卡壳。

### 病灶五：开场默认读者在听课

**症状**：开头直接上坏案例清单或下定义，缺少业务代入感。

**对策**：用场景假设式或业务价值式开场（经典句式："假设某系统面对……"），先让读者看见"业务上的问题"，再引出技术困境。

**边界（防过细）**：场景只用于**建立业务量级**（多少人、多大数据、什么输入特征），一句话到位；不要给人物写连续剧情、不要拟人化情绪（"张姐不敢再用了"式描写即越界）。Failure 用工程判断（"越过可用红线"），不用情绪判断。正反对照样例见 `examples/architecture-style-anchor.md` 样本六。

### 病灶六：判断句砸出、缺推导

**症状**：金句密度过高——"X 是第一纪律""Z 是 Y 的地基"，每句都像结论，读者没有跟随的推导过程。

**对策**：优先走"从问题出发"的推理链，让结论是推导的落点而非起点；金句收敛到段末一句。

### 病灶七：代码细节前置症——类名/路径/常量当叙述主线

**症状**：段落第一句就是类名、文件路径、常量值；读者还没明白"要解决什么问题"，先被要求记住一串标识符。整段读下来像 IDE 的代码导读，不像一篇能独立阅读的文章。

**根源**：把"代码即证据"误解为"代码即叙述"。代码引用是**锚点**，不是**主线**——主线永远是问题与方案。

**对策**：
- 段落先讲问题与方案，类名在读者知道"为什么需要它"之后才出现，作为锚点出现一次即可；
- 路径不进正文：课程文档正文只按类名引用，完整路径集中放附录代码索引表；讲义版可保留路径（讲师要在 IDE 里定位），但写成代码注释或括号附注，不做叙述主语；
- 常量值分级：只有"有信息量的数字"进正文（如 2000 字符上限、28 条拦截），ID 规则这类降为一句说明。

**示例**（课5 第三段改写前后）：
- ❌ "分片的前提是分类。入库管道的第一站不是切片，而是判断'这份文档是什么性格'——`docType` 决定用哪个 chunker……"
- ✅ "客服 Agent 的知识库里躺着五类资料：50 条商品描述、13 条促销活动、40 行订单记录……但向量数据库不直接吃文档。"（先看见业务，再看见技术）

### 病灶八：案例隔离症——工业案例只堆在文末

**症状**：正文证据全是项目内部细节（本项目改了什么、拦了多少条），工业界案例被统一隔离在文末"延伸阅读/备课参考"，正文一个都没有。读者看不到"业界也这么做"的佐证，方案的可信度和画面感都打折。

**对策**：**案例入正文，出处留文末**。正文中以一两句话引用工业案例（来源名称 + 关键数字/结论），URL 和完整出处仍留在延伸阅读区。判断标准：每个核心架构决策（分片策略、过滤建模、图谱建模等），正文至少有一处工业佐证。

**示例**（课5 改写后）：
> "langcopilot 团队对比了 9 种分片策略，语义感知的切法相比'固定窗口硬切'的朴素基线，检索质量最高提升约 70%……换句话说，分片不是'随便配个参数'的小环节，它是和选模型同等重要的架构决策。"

## 2. 病灶速查表

| 病灶 | 症状 | 对策 | 自检问句 |
|:---|:---|:---|:---|
| 电报体 | 破折号连排、主语缺失 | 改写成完整因果句 | 每句能否答出"谁/做了什么/为什么"？ |
| 清单体 | 表密排、无解读文字 | 表前一句 + 表后一两句解读 | 删掉表格后，上下文能否靠文字读通？ |
| 演进静态化 | 演进只出现在收口表里 | 正文贯穿"朴素→失败→方案→代价" | 每个方案是否讲清它补了上一方案哪一环？ |
| 术语无释 | 缩写首现即用 | 首现配一句大白话 | 首次出现的术语读者能立刻理解吗？ |
| 开场没代入 | 直接上清单/定义 | 场景假设式 / 业务价值式开场 | 读者先看见问题，还是先看见名词？ |
| 金句砸场 | 判断句密度过高 | 推理链先行、金句收尾 | 结论是推导的落点，还是开场的口号？ |
| 代码细节前置 | 段首即类名/路径/常量 | 问题与方案先行，代码引用为锚点、路径入附录 | 本段第一句是问题，还是标识符？ |
| 案例隔离 | 工业案例只在文末 | 案例入正文（来源+数字），出处留文末 | 每个核心决策，正文有工业佐证吗？ |

## 3. 叙述引入句式（可直接套用）

- "这个判断怎么来的？"
- "把演进脉络摆直："
- "它坏在'看起来没问题'的地方："
- "用一张表就能看明白："
- "要说清楚为什么这么分，把这一处单独拎出来："
- "要解释为什么……，先看它是怎么失败的："
- "理论落到实现，就是一张'留任清单'："

## 4. 落笔自检清单

- [ ] 每个段落是否有一条完整因果链（因为…所以…）？
- [ ] 每张表格前后是否有"解读文字"（表前一句 + 表后一两句）？
- [ ] 专业术语首现是否都有大白话解释？
- [ ] 段落之间是否用过渡句衔接，而非硬切？
- [ ] 正文是否体现"朴素做法 → 失败 → 方案 → 代价"的演进线（而非只有静态表格）？
- [ ] 删掉所有破折号连续注释后，句子是否仍完整可读？
- [ ] 金句密度是否 ≤ 每段一句？
- [ ] 段落第一句是问题与方案，还是类名/路径/常量？文件路径是否已收进附录索引？
- [ ] 每个核心架构决策的正文里，是否至少有一处工业案例佐证（来源+关键数字）？

> **Phase 5 必查项**：应用架构课与架构书的审查，除本清单全量自查外，病灶三（演进静态化）、四（术语无释）、五（开场没代入）、七（代码细节前置）、八（案例隔离）为**必查项**——这五条最直接影响"易读性"，必须逐段核对，不得抽样。

## 5. 与其他规范的关系

与 `quality-guide.md` 的边界：
- `quality-guide.md §4` 管课程文档文体底线（客观中立、无口语、可独立阅读）
- 本规范管"这层书面语写得像不像架构师在讲系统"——在底线之上做叙述升级
- 应用架构课程文档两者都要满足：先过 `quality-guide.md §4` 底线，再过本规范

与 `architecture-case-writing.md` 的关系：
- 后者管章节结构与表格规范，本规范管句段级叙述质量
- 两者配套使用，结构达标后再做叙述自检

与 `examples/architecture-style-anchor.md` 的关系：
- 本规范是**检查清单**——告诉你"不能写成什么样"
- 锚点样本是**质感参照**——告诉你"写成什么样算好"
- 写作顺序建议：动笔前通读锚点样本对齐质感，成稿后按本清单逐段自检
