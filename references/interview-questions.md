# 附录深入思考题方法论

本指南定义"附录深入思考题"的生产方法、质量标准、候选题生成路径和写作规范。
深入思考题放在每讲末尾附录位置，定位是**启发提高**（架构思维训练），面试素材是副产品，不是八股背诵。

---

| 配置项 | 默认值 | 可选项 |

## 2. 质量三优先级（逐条门禁）

> **唯一出处声明**：本文档是附录深入思考题质量判据 **F1-F10 的唯一定义**（三维度见本节，篇幅/不给答案等硬性规则见 §6.2、§7）；`phases/phase-5-review.md`、`references/anti-patterns.md`、`references/core-principles.md` 只引用编号，不复述判据。

按优先级从高到低，每道入选题目**必须**满足三条：

**① 考察知识结构而非记忆（F1）**
- 答案需要分层面/分维度组织（≥2 个维度）
- 不是"什么是 XX"这种单点定义题
- 不是背诵流程步骤

**② 紧扣本课但超纲（F2）**
- 题干锚定本课 Demo/项目的具体架构
- 但问题指向本课正文未覆盖的更深/更广维度
- 学完本课能想得到方向，但课上没给答案

**③ 有 trade-off（F3）**
- 没有唯一正确答案
- 核心是在约束条件下做选择
- 至少存在 2 个互相拉扯的权衡维度

## 3. 题目类型定义

### 3.1 架构题（默认 3 道）

锚定本课 Demo 架构，向上推演 1-2 个演进档位，考察：
- 知识体系完整性（能不能把零散知识点组织成架构决策框架）
- 领域经验（有没有见过类似场景的真实解法）
- 演进思维（能不能说清"为什么是这个顺序"）

**典型提问方式**：
- "如果要把本课的 XX 系统升级到 YY 场景，你会怎么重构 ZZ 模块？考虑 A/B/C 三个维度。"
- "从本课的 L0 单链路演进到 L2 生产级，中间要经过哪些关键架构决策？每一步解决什么问题？"

### 3.2 深度题（默认 1 道）

从本课一个关键技术决策点深挖，考察：
- 真实决策深度（为什么选 A 不选 B，试过哪些方案）
- 科学决策能力（有没有做过对比实验/基准测试/数据支撑）
- trade-off 意识（选 A 付出了什么代价，怎么缓解）

**典型提问方式**：
- "本课选了 XX 方案做 YY，如果让你重新选型，在什么条件下你会考虑 ZZ？两种方案的本质 trade-off 是什么？"
- "线上出现 ZZ 问题，本课的方案会怎么挂掉？你会怎么兜底？"

## 4. 候选题生成路径

候选题在 Phase 2 末尾产出，目标 8-10 张候选卡片，由用户挑选 4 道。

### 4.1 主路径 C：本课 Demo 架构 → 向上推演（出 3 道架构题）

**执行步骤**：

1. **定位坐标**：确定本课 Demo 在演进路线上的当前档位（S0-S4 / L0-L4）
2. **向上推演**：向上看 1-2 档，列出该档位的核心架构决策点：
   - 控制流域：编排粒度/状态管理/路由策略的变化
   - 能力域：工具/算子/服务的拆分与扩展方式
   - 交互域：协议/接口/数据契约的升级
3. **构造题干**：每个决策点构造一道题，三句话结构：
   - 句 1（场景锚定）："本课的 XX 系统是 YY 架构，适合 ZZ 场景。"
   - 句 2（升级需求）："如果要支持 WW（更大规模/更高可靠性/更多场景），..."
   - 句 3（问题抛出）："...你会怎么设计？考虑 A、B、C 三个维度。"
4. **设计追问链**：每道题 2 层追问，层层深入：
   - 追问 1：缩小到一个具体子决策（选型/参数/边界条件）
   - 追问 2：推向更极端的场景或反直觉的选择
5. **工业验证**：用网页检索验证推演方向：
   - 搜索词模式：`{技术关键词} + "architecture evolution" / "scaling" / "production" / "lessons learned"`
   - 信源：一线公司技术博客、Staff+ 工程师个人博客
   - 找到至少 1 篇工业界在讨论同一问题的文章作为来源

**示例**（BI Agent 场景）：
> 本课的 BI Agent 是单 Agent 五节点 Pipeline（Planner→SQL Gen→Execute→Retry→Chart），适合几十张表的单业务域场景。如果要支持几百张表、多业务域的企业级数据环境，纯靠 LLM 找表准确率会掉到 10% 以下。你会怎么重构架构？考虑语义层设计、任务拆分粒度、元数据管理三个维度。
> 追问 1：语义模型你会自己设计 Text-to-DSL，还是接现成的语义层（如 Looker Semantic Layer、dbt Semantic Layer）？选型依据是什么？
> 追问 2：如果选择 Multi-Agent 拆分，按什么维度拆最合理（数据源/分析类型/用户角色）？拆多了会带来什么新问题？
> 来源：Databricks 2025 "From Text-to-SQL to Semantic Layer Agents"

### 4.2 辅路径 A：架构演进文章 → 反向提炼（出 1 道深度题）

**执行步骤**：

1. **定向检索**：用网页检索搜索本课主题相关的架构文章：
   - 搜索词模式：`{本课核心技术} + "production" / "lessons learned" / "from prototype" / "踩坑" / "演进"`
   - 限定域名（可选）：`includeDomains` 指定大厂技术博客域名
2. **信源筛选**（按优先级）：
   - ⭐ 一线公司技术博客（Anthropic/Databricks/Confluent/字节/美团/阿里技术等）
   - ⭐ Staff/Principal 工程师个人博客
   - InfoQ/极客时间等技术媒体深度文
   - 高赞技术公众号长文
3. **找决策时刻**：读文章，找到作者"纠结过、试过多个方案、最终选了 X 因为 Y"的段落
4. **反向成题**：把作者的决策时刻变成问题：
   - 先给出当时的约束条件（规模/成本/团队等）
   - 问"如果你是当时的架构师，你会怎么选？"
   - 追问指向被放弃方案的代价或新的约束
5. **保留来源**：题目关联阅读直接指向这篇文章

**示例**：
> Anthropic 在上线 Prompt Caching 之前，Agent 场景下 System Prompt 重复传输导致 Token 成本居高不下。他们最终选择了前缀缓存（Prefix Caching）方案，而不是语义缓存或请求级缓存。如果你来设计 Agent 的 Token 成本优化方案，在什么条件下你会选前缀缓存，什么条件下你会选语义缓存？两者混用的话缓存一致性问题怎么解决？
> 追问 1：前缀缓存的命中率高度依赖 System Prompt 的稳定性，在多租户场景下（每个用户 System Prompt 不同），前缀缓存还有效吗？
> 来源：Anthropic 官方 Blog "Prompt Caching: Transforming Long Context AI Applications"（2024）

### 4.3 检索工具使用规范

**通道见 `references/evolution-roadmap.md` §3.4**（零依赖优先）。下列命令是 Exa 与 Jina Reader 的具体用法，不要求装 agent-reach。

核心命令：
```bash
# Exa 搜索架构文章
mcporter call 'exa.web_search_exa(
  query: "{技术关键词} architecture lessons learned production",
  numResults: 8,
  startPublishedDate: "2024-01-01"
)'

# 阅读文章全文
curl -s "https://r.jina.ai/{文章URL}"
```

新鲜度要求：架构文章 ≤ 2 年（比工业案例的 1.5 年略宽，因为架构经验沉淀周期更长）。

## 5. 候选题卡片格式

候选题输出到 `.course/{task_name}/phase-2/interview-candidates.md`，每张卡片格式：

```markdown
## 候选题 #N · {架构题/深度题}

**题目**：{场景化题干，2-4 句}

**追问链**：
- 追问 1：{具体子决策}
- 追问 2：{更极端场景或反直觉选择}

**质量维度检查**：
- [ ] 考察知识结构而非记忆
- [ ] 紧扣本课但超纲
- [ ] 有 trade-off

**来源依据**：{文章标题}（{URL}）
**建议入选**：是 / 否
**备注**：（可选，说明为什么这道题好/不好）
```

8-10 张卡片全部产出后，暂停等用户选择。用户选 4 道（或要求重拟/补充），确认后进入 Phase 3。

## 6. 终稿写作规范

### 6.1 整体结构

```markdown
## 附录 A：深入思考题

> 以下问题不附标准答案，旨在锻炼架构思维与决策能力。建议在完成本课代码实践后，先自行组织答案框架，再结合"答题骨架"对比思路差异。

### A.1 {题目标题}（架构题）

{场景化题干，2-4 句}

**追问 1**：{...}
**追问 2**：{...}

**【答题骨架】**

- **核心思路**：{2-3 句话说清大方向，不展开细节}
- **关键权衡**：
  - {trade-off 1}：{一句话说明矛盾双方}
  - {trade-off 2}：{一句话说明矛盾双方}
- **延伸方向**：{1-2 个可以再深入的点，点到为止}

**【关联阅读】**
- [{文章标题}]({URL})

### A.2-A.4 同格式
```

### 6.2 硬性规则

1. **篇幅（F9）**：4 道题总篇幅 ≤ 讲义总篇幅 15%
2. **不给完整答案（F5 答题骨架 / F10 不给逐字答案）**：只给答题骨架，不给逐字答案
3. **追问链（F4）**：每道题 2 层，层层深入（不是平行问题）
4. **关联阅读（F6）**：每道题至少 1 条工业界真实来源
5. **场景锚定（F2 的题干要求）**：题干必须提到本课 Demo/项目的具体元素（类名/模块名/架构形态），不能出放之四海皆准的泛题
6. **标签标注（F8 题型配比）**：每道题标注类型（架构题/深度题）

## 7. 反模式清单（直接丢弃）

| 反模式 | 为什么不行 |
|:---|:---|
| "什么是 XX？"/"XX 的步骤是什么？" | 基础知识背诵题，违反质量① |
| 题目和本课 Demo 无关 | 通用八股，违反质量② |
| 有唯一标准答案（如"最佳实践是 XX"） | 没有 trade-off，违反质量③ |
| 追问是平行问题（"还有什么其他方案？""那 B 呢？"） | 不深入，违反追问链设计 |
| 给完整标准答案或长篇参考解析 | 变成"背题"，违反启发定位 |
| 用通用 WebSearch 搜"XX 面试题"凑数 | 出来的都是八股，质量无保证 |
| 跳过候选题 → 人工确认直接写终稿 | 流程违规，无法保证质量 |
| 附录题超过讲义 15% | 抢正文戏份 |
