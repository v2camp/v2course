# 课程讲义品质提升专项指南 (Course Quality Enhancement Guide)

本指南旨在解决讲义与大纲在生产中的三大核心顽疾：
1. **措辞生硬、模型味儿重（“AI 腔”）**
2. **图像生成弱，容易退化为文本/ASCII 示意图**
3. **讲义结构过于“讲师中心化”，忽略了学员、运营和求职/面试的多重视角**

---

## 1. 去 AI 腔与口语拟真标准 (AI-isms Eradication & Conversational Realism)

高质量的讲义应当听起来像是一个**拥有多年大厂实战经验、幽默风趣、说话一针见血的技术 Leader / 资深架构师**在面对面授课，而不是一本照本宣科的学术教科书。

### 1.1 衔接词禁用与替换对照表 (Blocklist & Replacements)

严禁在文档、讲义、大纲中出现以下高频“AI 腔”词汇，必须用更接地气的工程口语进行替换：

| 禁用词（AI 腔） | 推荐替换（工程拟真口语） | 示例场景 |
| :--- | :--- | :--- |
| **首先 / 其次 / 再次 / 综上所述** | **咱先看... / 紧接着... / 简单来说... / 说白了** | 逻辑排比与总结 |
| **不可否认的是 / 扮演着不可或缺的角色** | **这是核心需求 / 这是刚需 / 没它不行** | 强调重要性 |
| **值得注意的是 / 需要指出的是** | **这里有个容易踩坑的地方 / 敲黑板 / 面试中常被问到** | 引起注意 |
| **通过...我们可以实现...** | **搞定这个，就能比较轻松地完成... / 就能实现...** | 描述收益 |
| **如前所述 / 正如前面所提到的** | **刚才咱聊到了... / 回顾一下刚才那步...** | 上下文桥接 |
| **具有里程碑意义的 / 革命性的** | **生产级方案 / 企业级组件 / 核心技术选型** | 夸赞技术 |
| **我们应该 / 建议采取...** | **建议直接使用... / 推荐选择...** | 给出建议 |

### 1.2 痛点前置与技术动机阐明 (Problem-First & Technical Motivation)

每一个技术点或架构引入，必须遵循 **【问题场景 → 技术动机 → 方案引入 → 效果说明】** 的平实四阶段，避免无动机的技术罗列：

*   **❌ 平庸（AI 腔）**："Qdrant 是一个高效的向量数据库。在生产环境中，纯内存向量库会丢失数据。因此，我们需要使用 Qdrant 替换它以实现持久化。"
*   **✅ 平实技术动机**："上节课的 RAG 用了内存向量库。在开发阶段运行正常，但生产环境中如果服务重启，内存中的向量数据会全部丢失。这意味着需要重新调用 Embedding API 生成向量，既耗时又增加成本。为了解决这个问题，我们需要将向量存储从内存迁移到 Milvus 向量数据库。Milvus 提供磁盘持久化，服务重启后可以快速恢复数据。"

> ⚠️ **【硬性硬约束】情绪张力调动必须严格基于真实案例**
> 所有的情绪张力、痛点冲突与窒息现场，**必须完全依据用户给出的实际业务案例、技术事实或研发排障经历进行编写，绝对禁止凭空捏造、杜撰虚假的戏剧化场景或非事实技术情节**。
> 如果用户给出的原始案例信息不足以支撑情绪张力，**必须在讲义撰写之前主动与用户沟通商讨、补充事实细节**，而不是自主进行文学创作、夸张或胡编。

## 2. 扁平化深度干货输出规范 (Factual & Flat Wording Style)

大纲与讲义虽然服务于多种角色（讲师授课、学员阅读、求职面试等），但**在正文排版中绝对禁止使用任何角色特化的形式卡片**，避免夸张、浮夸、绝对化的词汇，实现统一、纯粹的“技术干货”输出。

### 2.1 彻底封杀三大角色卡片组件

在讲义正文及大纲中，**绝对禁用并彻底删除以下三种具有特定角色标签和隔离特征的卡片组件**：
*   ❌ `💡 [讲师侧记]`
*   ❌ `⚠️ [学员踩坑警告]`
*   ❌ `🎯 [面试突围金句]`

### 2.2 统一采用平实中立的干货词汇承载内容

不针对特定角色单独作提示，而是将所有有价值的内容转化为通用、高质量、可以直接阅读的知识体系。一律使用 **【要点】**、**【知识点】**、**【敲黑板】** 等平实工程口语表达来高亮和组织干货：

*   **【要点】**：承载核心操作步骤、命令行演示、重点执行代码。
    *   *示例*：
        *   **【要点】**：进入 `projects/ts/apps/lesson6-rag-bot/` 目录，运行 `pnpm test` 启动测试套件。
*   **【敲黑板】**：承载容易踩坑的网络、依赖、环境、配置等排障方案。
    *   *示例*：
        *   **【敲黑板】**：调用 OpenAI Embedding 接口时，若未配置正确的本地代理会报 `ETIMEDOUT`。请务必检查 `.env` 文件中的 `HTTP_PROXY` 是否对齐。
*   **【知识点】**：承载深度的技术方案、底层架构原理、生产级核心设计（原本面试金句等内容转化为深度知识点）。
    *   *示例*：
        *   **【知识点】多部门敏感数据隔离实现**：
            我们在生产实践中，并没有采用简单在应用层做过滤的软隔离（极易因代码漏洞产生数据越权），而是采用 **JWT 鉴权 + 向量库元数据过滤（Metadata Filtering）的双层物理级隔离**。
            用户请求携带的 JWT 解析出 department 后，透传给向量库（如 Qdrant）的检索请求，在 filter 条件中强制绑定 `department = financial`。这直接在向量索引检索阶段（HNSW 搜索）就把不合规的 Chunk 过滤掉了，不仅绝对安全，还极大减少了向量相似度计算开销。

**金句处理规范：**
- 禁止使用"金句""面试突围金句""结束金句"等字眼
- 原"金句"内容统一转化为"收口"段落，以平实表述承载
- 收口段落通过 `**【知识点】标题**` 格式承载技术深度
- 讲义不预设"一句话总结"，由讲师在直播现场即兴把控

### 2.3 教学标注补齐优先级
教学标注补齐按以下优先级执行，不得跳级：
1. 优先对已有内容进行标注（从导出版或已有文本中识别）
2. 若无现成内容，从原文类似含义内容微调后标注
3. 仅当以上两者都不支持时，才进行适度创作

标注密度控制：
- 每个 Step 最多 2 个标注（1 个【知识点】+ 1 个【要点】或【敲黑板】）
- 全文【敲黑板】控制在 5 个以内，避免标注疲劳

### 2.4 严禁夸大、绝对化或针对特定角色的浮夸词汇

输出干货时，必须用最朴实、直接、硬核的代码和架构说话，**无需用夸大或绝对的手法来给出针对某个角色的提示**：
*   **严禁使用**：“闭眼背诵”、“职级差回答（背诵版）”、“让面试官刮目相看”、“降维打击面试官”、“阿里 P7 / 腾讯 10 等级神级话术” 等浮夸功利的宣传词、角色修饰词。
*   **坚持事实与深度**：去掉这些功利化包装后，保留其最硬核、最纯粹的架构思维与大厂生产实践方案，直接用客观、专业的技术术语在 **【知识点】** 中呈现。

## 3. 制图规范（v2svg 驱动）

架构图 / 流程图 / 序列图一律走 v2svg 生成，禁止模型手写 SVG、手写坐标或主观选配色。调用约定、三域 role 配色、回执驱动的质量门禁见 `references/diagram-integration.md`。

- 禁止使用 ASCII 字符或简易表格草率画流程图。架构/流程/序列图一律走 v2svg（IR→validate→render）生成独立 SVG，再用 Markdown 引用。
- 配色 / 字体 / 字号 / 箭头 / 暗色模式等由 v2svg 统一（三域 role 配色），course-skill 不再规定具体色值或坐标；详细规范在 v2svg 自身文档。

> 以下 `### 3.3` 为**普适图片规范**，覆盖所有图片（含截图 / 位图 / 外部图），与 v2svg 互补共存，不得因改用 v2svg 而删除。

### 3.3 图片文件与引用规范（普适规范，覆盖 SVG / 位图 / 图表）

本规范适用于**所有图片资源**（SVG 矢量图、PNG/JPG 位图、图表截图、数据图），不限于 SVG。

1.  **独立存储，禁止任何内嵌**：任何图片**一律禁止以 base64 或 data URI 形式直接写在 Markdown 文档中**，包括 `![](data:image/png;base64,...)`、`![](data:image/svg+xml;base64,...)` 等形式。所有图片必须以独立文件存放在当前课程目录下的 `images/` 子文件夹中，用相对路径引用。
2.  **SVG 优先**：架构图、流程图、拓扑图、对比图等图形化表达，优先产出 SVG 矢量图（可无损缩放、飞书/Obsidian 双端兼容），不要用 PNG 位图。
3.  **位图/图表的处理**：确需使用位图（如数据曲线图、真实截图）时，保存为独立 PNG/JPG 文件存入 `images/`，同样以相对路径引用，禁止 base64 内嵌。
4.  **数据表格优先用 Markdown 表格**：指标对比、评测结果、数据列表等**结构化数据**，优先用 Markdown 表格呈现（应用架构课遵循 `references/architecture-course.md` 的指标对比表规范），**不要生成截图**。只有确需可视化趋势/结构关系时才配图。
5.  **绝对禁止 ASCII 图**：扫描到 `┌─┐` 或 `| --> |` 等 ASCII 字符，一律走 v2svg 渲染（IR→validate→render）重构为 SVG。
6.  **引用路径**：使用相对路径引用，如 `![RAG 四步链路](./images/rag-4-steps.svg)`、`![分片策略评测曲线](./images/sharding-eval-curve.png)`。

## 4. 课程文档文体规范（学员视角）

本规范适用于面向学员的**课程文档**——即从讲义转换而来、学员可以直接当教程读的技术文档。核心目标：客观、专业、高密度、可独立阅读。

### 4.1 核心原则

课程文档不是"讲义去掉几个词"，而是一次完整的**文体重构**——从"讲师对学员说话"转为"技术文档对读者说话"。

| 原则 | 说明 | 反例 |
|:---|:---|:---|
| **客观中立** | 不使用第一人称复数呼语，不假设读者在"听课" | ❌ "我们来看这段代码"、"大家注意" |
| **书面技术语** | 用精确、专业的技术表达，不用工程黑话或口语化表达 | ❌ "搞定这个"、"平趟过去" |
| **可独立阅读** | 读者不需要听过课，直接读就能理解完整逻辑 | ❌ "上节课我们讲了..."（应改为"前置知识：..."） |
| **知识密度高** | 去掉口播冗余、互动环节、重复强调，保留纯粹知识 | ❌ "这个点非常重要，我再强调一遍" |
| **结构清晰** | 章节层级分明，读者可以快速定位和检索 | — |

### 4.2 人称与语气转换对照表

| 讲义（讲师口语） | 课程文档（技术书面语） | 场景 |
|:---|:---|:---|
| 咱先看... | 以下示例展示... / 首先观察... | 引入例子/代码 |
| 我们来实现一下... | 实现步骤如下： / 具体实现： | 引入操作 |
| 大家注意 / 大家看这里 | 需要注意的是 / 此处需要关注 | 引起注意 |
| 敲黑板 | **注意** / **常见问题** / ⚠️ **提示** | 强调易错点 |
| 我给大家演示一下 | 操作演示： / 执行以下操作： | 引入演示 |
| 刚才咱聊到了... | 如前所述 / 前文提到 | 上下文桥接 |
| 说白了 / 简单来说 | 简而言之 / 核心是 | 总结概括 |
| 这玩意儿 / 这东西 | 该组件 / 此模块 / 该机制 | 指代事物 |
| 搞定 / 整完 | 完成 / 实现 / 执行完毕 | 描述完成状态 |
| 踩坑 | 常见问题 / 易错点 / 注意事项 | 描述问题 |
| 【知识点】 | 保留【知识点】 | 深度内容 |
| 【要点】 | 保留【要点】 | 操作步骤 |
| 【备课参考】 | 【延伸阅读】（筛选后保留） | 延展阅读 |

### 4.3 内容取舍规则

#### 保留的内容
- ✅ 核心技术原理和架构设计
- ✅ 代码示例（但讲解方式从口播式转为注释式）
- ✅ 【知识点】和【要点】干货标注
- ✅ 架构图/流程图（v2svg 渲染的 SVG）
- ✅ 问题场景和技术动机（但表达方式转为客观描述）
- ✅ 深入思考题题干和追问
- ✅ 来源与参考链接
- ✅ 从备课参考中筛选出的、对学员有价值的【延伸阅读】

#### 移除的内容
- ❌ 所有讲师视角的提示（演示动作、操作步骤描述、节奏提示）
- ❌ 所有教学钩子（挖坑/填坑、互动设计、课堂提问）
- ❌ 直接呼语（"同学们"、"大家"、"你"）
- ❌ 第一人称复数（"我们"、"咱"）
- ❌ 情绪化/戏剧化表达（"深夜线上事故"、"窒息现场"等——保留问题，但用客观语言描述）
- ❌ 口播冗余（重复强调、过渡性废话、"这个点非常重要"之类）
- ❌ 深入思考题的答题骨架（只留题干和追问，不给参考思路）
- ❌ 【备课参考】中过于深入、不适合学员阅读的内容（如讲师培训材料、内部技术评审文档）

### 4.4 代码讲解转换规则

讲义中的代码讲解是"逐行口播式"（带着学员一行行读），课程文档中应转为"代码+注释式"（代码自带说明，读者自己读）。

**讲义写法（讲师视角）**：
> 咱来看这段代码。第 3 行，这里调用了 `search()` 方法，传入查询词和返回数量。为什么要传 limit？因为如果不限制返回数量，向量库可能返回几百条结果，既浪费资源又没用。所以这里我们限制返回 top 10。

**课程文档写法（学员视角）**：
> 调用 `search(query, limit)` 方法执行向量检索：
> - `query`：检索查询词
> - `limit`：返回结果数量上限，避免返回过多无关结果（默认 10）
>
> ```python
> results = vector_store.search(query=user_query, limit=10)
> ```

### 4.5 情绪张力转换规则

讲义的"痛点冲突"是戏剧化的（"深夜三点线上告警"、"老板在群里@你"），课程文档中应保留问题场景和技术动机，但表达方式转为客观描述。

**讲义写法**：
> 凌晨三点，运维群里突然炸了——客服系统全挂，用户消息全部发不出去。老板在群里连环 @，你睡眼惺忪地爬起来查问题。排查了半天才发现，是内存向量库重启后数据全丢了。这种事儿谁遇到谁崩溃。

**课程文档写法**：
> 内存向量存储存在以下问题：
> - **数据持久化缺失**：服务重启后向量数据全部丢失，需要重新生成 Embedding，耗时且增加 API 成本
> - **可用性风险**：单实例部署下，服务故障会导致整个检索功能不可用
>
> 为解决上述问题，需要引入持久化向量数据库（如 Milvus、Qdrant），将向量数据存储到磁盘，服务重启后可快速恢复。

### 4.6 课程文档品质红线

课程文档必须满足以下红线，否则判定为不合格：

1. **零讲师口语残留**：不得出现"咱"、"大家"、"我们来看"、"敲黑板"（转为"注意"）等典型讲师口语
2. **零教学提示残留**：不得出现演示动作、挖坑/填坑、互动设计、讲师侧记等教学专属内容
3. **技术含义无偏差**：去口语化后，技术内容的准确性和完整性不得下降
4. **可独立阅读**：读者不需要依赖讲课语境，直接阅读能理解完整的技术逻辑
5. **结构与讲义一致**：章节/分段结构与讲义 1:1 对应，不增删结构层级

## 6. 教学钩子"挖坑/填坑"管理

### 6.1 挖坑
在讲解中设置悬念或问题，标注为：
> **挖坑**：[内容] 【[填坑时机]】

填坑时机标注规则：
- 本课闭环：标注"本课填坑"
- 后续课时填坑：标注"课时N填坑"（无需赘述后续课时如何填坑的具体内容）

### 6.2 填坑
仅在本课内回应的挖坑需要完整填坑描述，标注为：
> **填坑**：[内容]（回应 [挖坑位置]）

对于后续课时的填坑，本课中只需标注"课时N填坑"即可，不必赘述后续课时如何填坑的具体内容。

### 6.3 闭环管理
- 每个挖坑需标注填坑时机
- 全文挖坑不超过 5 个
- 本课内闭环的填坑至少 1 个
