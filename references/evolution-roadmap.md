# 架构演进路线方法论（Evolution Roadmap）

本指南定义实战课系列讲义中"架构启示与演进路线图"段落的生产规范。
适用于系列实战课的收口段设计，确保每课时既有"本课实现了什么"的落地感，
又有"下一步往哪走"的方向感。

---

## 1. S0-S4 通用演进模型

五档模型描述"从最小原型到生产级系统"的通用演进路径。
各档位是架构形态而非具体技术选型，适用于 AI Agent、数据工程、微服务、
前端工程等多个技术领域。

| 档位 | 名称 | 核心特征 | 解决什么问题 |
|:---|:---|:---|:---|
| **S0** | 能用 | 单点原型、最小闭环、单线程执行 | 跑通核心链路，证明方案可行 |
| **S1** | 可控 | 拆分编排、计划-执行分离、显式状态管理 | 方向漂移、执行失控、不可中断 |
| **S2** | 多源 | 多路能力接入、融合排序、数据质量治理 | 来源单一、结果被低质量源污染 |
| **S3** | 并行 | Orchestrator-Worker 多节点协作、并行调度 | 上下文装不下、串行执行慢、任务复杂度超限 |
| **S4** | 好用 | 上下文工程、评估闭环、灰度发布、可观测 | 行为不可观测、回归无保障、上线风险高 |

### 档位合并规则

若本课主 Demo 已实现了 S0+S1（如直接采用 Plan-Execute 拆分架构），
起点档记为 S0+S1，不强行拆为两档。演进图可画为 4 档或更少。

### 档位适用边界

- 不是所有课程都需要走完 S0→S4。单节课/迷你课不需要演进路线段。
- 系列实战课中，不同课时落地不同档位，但每节课的收口段必须让学员知道
  "当前在 S 几、下一档解决什么问题"。

## 2. 三域抽象模型

架构分析使用三域视角。**配色由 v2svg 统一，权威定义见 `diagram-integration.md` §1（role 枚举表）；本文件不复述色值或 role 清单。**

| 域 | 含义 | Agent 领域映射 | 数据工程映射 | 微服务映射 |
|:---|:---|:---|:---|:---|
| **控制流域** | 编排、调度、状态机、流程控制 | Context/Graph 编排 | DAG Scheduler | Orchestrator/Service Mesh |
| **能力域** | 工具、算子、外部系统、业务能力单元 | Tools/Function Calling | Operators/Connectors | Services/Adapters |
| **交互域** | 协议、接口、数据契约、输入输出 | Protocol/LLM I/O | Data Schema/API | API Gateway/Event Contract |

具体领域可做领域化命名；三域到 v2svg role 的对应（控制流→`control`／能力→`capability`／交互→`interaction`）由 v2svg 定义。

## 3. 工业案例调研规范

### 3.1 新鲜度硬约束

- 案例发布/分享时间**不得早于当前日期往前推 1.5 年**（约 547 天）
- 调研时必须标注案例发布日期，超期必须替换

### 3.2 真实度硬约束

- 必须是**实际工业应用**（已在生产环境运行），非实验室 Demo、非营销软文
- 必须包含**量化指标**（≥3 项，选自性能/成本/延迟/可靠性任一维度）
- 必须有**架构拓扑图或关键设计文档**可引用
- 禁止：凭空捏造案例、合成多个案例、引用未验证的二手转述

### 3.3 信源优先级

1. **一线技术公司工程博客**（Anthropic / Netflix / Uber / Meta / ByteDance / Google / LinkedIn / Slack / Stripe 等 Engineering Blog）
2. **顶级技术会议分享**（QCon / KubeCon / Strange Loop / SIGMOD / VLDB / USENIX 等）
3. **企业技术白皮书 / 开源项目 RFC / Architecture Decision Record**
4. **高质量技术媒体深度报道**（如 The New Stack、InfoQ 深度长文）

### 3.4 调研通道（零依赖优先）

工业案例调研只需要两种能力：**搜**和**读正文**。按下面的顺序取，前两档零安装零 Key，足够覆盖本 skill 的全部场景：

| 档 | 做什么 | 怎么用 | 依赖 |
|:--|:--|:--|:--|
| ① 检索 | 找一线工程博客、GitHub RFC/ADR、会议与白皮书 | 平台自带的 WebSearch（宿主 Agent 一般内建） | **无** |
| ② 读正文 | 把检索到的 URL 转成可引用的干净 Markdown | `curl -s "https://r.jina.ai/<URL>"` | **无**（Jina Reader 免 Key、不扣 token、20 RPM，个人调研足够） |
| ③ 增强（可选） | 语义检索更准；或需要 Twitter / Reddit 上的工程讨论 | Exa（免费额度）或 agent-reach skill | 需安装/Key |

**为什么把 agent-reach 放第三档而不是第一档**：它需要 Python 3.10+ + pip + Node/npx + mcporter + gh CLI + yt-dlp 等一串依赖，价值主要集中在社交平台（Twitter / Reddit / 小红书 / B站）与视频字幕——本 skill 的调研对象是工程博客与 RFC，用不到这些。而它的"读网页"能力本质上就是调 `r.jina.ai`（②档）。**能零依赖做完的事，不要用需要安装的工具做**——技能被分发到不同宿主时，装不上的依赖就是断掉的链路。

检索路径：一线工程博客 → GitHub RFC / Architecture Decision Record → 顶级会议分享与技术白皮书（补充）。

关键词生成策略：
- 通用模板：`{领域} architecture evolution production case study`
- 短板反推：基于 S0 起点的实际失败模式，反推下一档关键词
  （例：若 S0 瓶颈是"方向漂移"→ 搜 `plan-execute agent production architecture`）

### 3.5 必须采集的信息

每个工业案例必须采集：

| 字段 | 说明 |
|:---|:---|
| 案例名 | 公司/团队 + 系统名 |
| 来源 URL | 原始链接（非二手转述） |
| 发布时间 | YYYY-MM，用于新鲜度校验 |
| 工业应用证明 | 用户规模/请求量/业务场景 |
| 量化指标 | ≥3 项（性能/成本/延迟/可靠性） |
| 架构拓扑 | 引用原图或描述关键拓扑 |
| 演进驱动力 | 为什么从 N 档演进到 N+1 档，真实业务/技术瓶颈 |
| 使用语境 | 在本课哪个档位引用 |

### 3.6 案例新鲜度自检表

交付前必须填写：

| 案例名 | 来源 | 发布时间 | 距今天数 | 工业应用证明 | 量化指标 |
|:---|:---|:---|:---|:---|:---|
| {案例1} | {URL} | {YYYY-MM} | {N天} | {规模/场景} | {3项+} |

距今天数 > 547 天 → 必须替换。

## 4. 失败模式推导方法

失败模式不能套模板，必须基于本课主 Demo 的实际短板枚举。

### 推导步骤

1. **审视本课主 Demo 的硬限制**：哪些约束是代码里明确写的？
   （如：maxSteps=5、只有 web_search 一个工具、无并发、无持久化、无评估）
2. **转化为失败场景**：在什么真实任务下，这些硬限制会导致失败？
   （不是"理论上不够好"，而是"在 X 场景下一定失败"）
3. **归类到三域**：每个失败模式根因在哪个域？
   - 控制流域瓶颈 → S1/S3 解决
   - 能力域瓶颈 → S2 解决
   - 交互域瓶颈 → S4 解决

### 失败模式表格模板

| 失败场景 | 表现 | 根因（架构层面） | 由哪一档解决 |
|:---|:---|:---|:---|
| {具体场景} | {具体表现} | {架构层根因} | {S1/S2/S3/S4} |

### 注意事项

- 每档最多 3 类失败模式，不要贪多
- 失败模式必须对应到明确的后续档位，不能留"永远解决不了"的项
- 调参能解决的不算架构瓶颈（如"温度参数设太高导致输出不稳定"不算）

## 5. 演进路线段四段式骨架

实战课收口段统一用四段式结构，约 10 分钟：

### X.1 当前坐标（2min）

- 【知识点】三域地图：本课实现的架构在三域中各覆盖了什么
- 表格：手写实现 vs 框架实现的三域映射
- 与前序课程的能力进阶对照
- 收束：这只是演进的起点

### X.2 为什么只是起点（2min）

- 3 类失败模式表格（表现/根因/由哪档解决）
- 【敲黑板】：架构瓶颈，调参解决不了

### X.3 演进路线图（5min）

按 S0→S4 顺序（或合并档位），每档包含：
- 图引用（每档至少 1 张，由 v2svg `flow` 渲染，`stages` 对应档位）
- 核心变化（一句话）
- 解决什么（对应 X.2 哪个失败模式）
- 工业案例佐证（≤1.5 年，附来源链接 + 发布时间）
- 关键工程要点（3-4 条）
- 本质金句（一句话收束本档的本质）
- 【敲黑板】（仅关键档位，标出代价/边界，如多 Agent 的 Token 成本）

### X.4 收口矩阵（1min）

- 三域 × 各档位演进矩阵表格
- 一句话定位本课落点
- 后续课程 handoff（下节课讲哪一档）

## 6. SVG 设计规范补充

### 6.1 evolution-roadmap.svg（总图）

- 类型用 v2svg `flow` + `stages`（档位即 stage）；图布局与尺寸由 v2svg 自动布局，course-skill 不再规定坐标或 viewBox。
- 总图按 S0→S1→S2→S3→S4（或合并后档位）依次排列，每个档位作为一档 stage。
- 每个卡片标注：档位名、一句话描述、对应课时（若已规划）。
- 本课所在档位高亮标注（如 "✅ 本课"）。
- 底部附三域 × 档位矩阵（可简化版）。

### 6.2 档位拓扑图

- 类型同样用 v2svg `flow` + `stages`；每档至少 1 张，展示该档位的核心拓扑变化，布局由 v2svg 自动决定。
- S1 Plan-Execute：展示 think 拆分为 planner+executor
- S2 多源融合：展示多路工具 + Rerank
- S3 多 Agent：展示 Orchestrator + 并行 Worker
- S4 工程化：展示上下文工程 + 评估闭环
- 配色由 v2svg 统一（role 配色，见 `diagram-integration.md` §1）。

### 6.3 外部架构图引用

引用外部企业架构图（如 Anthropic Multi-Agent 架构图）时：
- 必须标注来源：公司名 + 博客标题 + URL
- 保持原图布局，不重新绘制（避免篡改原意）
- 若使用 Markdown 图片引用外部 URL，需同时评估国内可访问性；
  不可访问时应下载为本地 SVG 存入 images/，并保留 attribution
- 引用格式：`> 架构图来源：{公司} {博客标题} {URL}`

## 7. 代码评估原则

演进路线图是"架构方向认知"段，不是"代码实战"段。
评估代码是否需要重构的判断标准：

- **不需要重构**：本课代码已完整实现起点档（S0 或合并档）的所有要素
- **需要对齐**：代码实现了起点档，但讲义描述的架构与代码有偏差 → 修改讲义对齐代码
- **需要重构**：代码未实现起点档核心要素（如声称是 Plan-Execute 但代码仍是 ReAct 循环）
  → 重构代码，但这属于开发任务不在本 skill 生产流程内，需与用户确认

判断结论：如果代码与讲义起点档对齐，明确标注"不需要重构"并给出依据。
