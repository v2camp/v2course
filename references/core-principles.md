# 核心原则

## 触发即进入本 Skill 的工作方式

只要用户在策划、编写、优化以下内容，就必须默认进入本 skill 的流程：
- 各类课程的策划与制作。
- 职业辅导脚本。

## 八项核心原则

### 1. Plan 驱动与 Plan Agent
进入任务后，必须先调用 `enter_plan_mode`。对于复杂任务，应考虑调用 `plan agent` 细化步骤。

### 2. 先确认时长与规范，后开始内容
禁止在未确认"课程时长"和"命名规范示例"的情况下开始生产。时长是评估内容密度的核心标尺。

### 3. 多版本 L1-L4 分层同步
多版本管理遵循四层分层：
- **L1 产品体验 / L2 架构逻辑 / L3 工艺规范** → 必须一致
- **L4 技术实现** → 各自独立，不做类名/方法级 1:1 翻译映射
- 写各自技术栈最地道的实现，而不是另一栈的翻译腔
- 详见 `phases/phase-0-explore.md`（多版本识别）与 `phases/phase-4-sync.md`（L0-L4 对齐清单）

### 4. 工业案例新鲜度与 agent-reach 调研
- 凡是引用工业案例（尤其是演进路线段），发布时间 ≤ 1.5 年，必须有量化指标和来源标注
- Phase 2 工业案例调研优先通过 agent-reach skill 执行；若 agent-reach 不可用，可使用 WebSearch + WebFetch 组合替代，但必须遵循相同的信源优先级和新鲜度约束
- 详见 references/evolution-roadmap.md §3

### 5. 过程文件隔离
禁止在课程正式目录下创建任何过程文件夹（如 `_process`）。所有过程产物（草稿与各阶段正式产出）必须统一存储在 `.course/` 下，按任务名隔离；课程目录只放正式交付物。

路径规则：
- 若有已选择的项目目录 → 项目根目录下的 `.course/{task_name}/phase-n/`
- 若无项目目录（仅临时工作区） → 当前工作目录下的 `.course/{task_name}/phase-n/`

### 6. 视角 A-H 评估门禁（共八个）
所有产出物必须通过 Phase 5 的**视角 A-H** 审查，不合格必须重做。**逐条判据的唯一出处是 `phases/phase-5-review.md` §2**，本文件只列索引、不复述判据：

| 视角 | 名称（课型适用见括号） |
|:---|:---|
| A | 流量运营与转化（公开课/录播课对应大纲；实战课对应讲义） |
| B | 讲师授课（对应讲义） |
| C | 学员学习（对应课程文档） |
| D | 深度技术架构（讲义 + 课程文档） |
| E | 演进路线专项（系列实战课必检） |
| F | 附录深入思考题专项（**F1-F10**，实战课必检） |
| G | 代码引用与飞书兼容专项（**G1-G10**，应用架构课必检） |
| H | 教学代码生产级门禁专项（**H1-H8**，实战课必检；含代码对照与接线核验） |

> 计数口径：早期写作"三视角"、扩章后写作"六视角"，**实际为 A-H 共八个**——涉及视角数量时一律以此表为准。四项专项（E-H）的条目编号只在 `phase-5-review.md` 定义，引用时须同时给出条目编号与文件位置。

### 7. 附录深入思考题质量门禁（实战课）
- 实战课默认每讲附录 4 道深入思考题（3 架构题 + 1 深度题）
- 每道题必须通过三质量维度：考察知识结构而非记忆 > 紧扣本课但超纲 > 有 trade-off
- Phase 2 必须先产出 8-10 张候选题卡片，经用户人工确认选 4 道，禁止跳过直接写终稿
- 终稿只给答题骨架不给标准答案，每道题必须有至少 1 条工业界关联阅读
- 详见 references/interview-questions.md

### 8. 实战课·应用架构专项原则
实战课·应用架构是基于**已有完整生产级代码**的架构解读课，与"从零写代码"的实战课·基础/实战本质不同，必须遵循以下原则：

#### 8.1 代码先行原则
- **必须先有代码**：必须等独立开发Agent完成代码开发、评测指标达标后，才能开始写讲义
- 禁止"先写讲义再补代码"，禁止凭设计稿猜测代码结构
- 若开发过程中架构发生调整，必须等代码稳定后再更新讲义，讲义始终以**最终可运行代码**为准

#### 8.2 代码引用零容错原则
- 讲义中引用的**所有**类名、方法名、文件路径、包结构必须100%准确
- 引用代码前**必须先Read真实文件**，禁止凭记忆或设计稿猜测
- 代码引用规范详见 `references/code-reference-feishu.md`

#### 8.3 子系统演进叙事原则
- 不是"今天我们来写XX模块"，而是"XX模块从最简Baseline演进到生产级，经历了哪些阶段，每一步解决了什么问题，做了什么trade-off"
- 每个核心模块必须有**演进阶梯**：Baseline有什么问题→第一步优化解决了什么→带来什么新问题→下一步优化→...→最终生产级方案
- 演进不是"拍脑袋的过度设计"，而是"被问题推着走"——每一步优化都要有对应的问题场景和量化收益

#### 8.4 量化驱动原则
- 每节课必须有**明确的量化指标对比表**：Baseline指标→各阶段优化后指标→最终指标
- 指标必须可验证：通过评测脚本可复现，不是拍脑袋的数字
- 每个优化点必须对应量化收益："加了Rerank之后，Precision@5从60%提升到90%"，而不是"效果变好了"

#### 8.5 评测闭环原则
- 评测集和评测脚本不是附属品，是课程核心资产的一部分
- 讲义中必须演示如何运行评测、如何看评测报告、如何根据bad case迭代优化
- 评测集必须覆盖：正常case、多轮case、边界case、攻击case（注入/越权）

#### 8.6 架构决策原则
- 不仅讲"怎么做"，更要讲"为什么这么做，为什么不那么做"
- 每个关键架构决策必须有**选项对比**：至少2-3个备选方案，说明为什么选了当前方案，trade-off是什么
- 要明确讲"什么时候不需要这个设计"——避免学员学了之后到处过度设计（如"客服场景单Agent足够，不需要Multi-Agent"）
- 详见 references/architecture-course.md

## 反绕开原则

以下行为被视为绕开本 skill，必须纠正：
- 在没有命名规范示例的情况下盲目创建目录。
- 在 Phase 0/1/2 未完成前直接跳到 Phase 3 写稿。
- 为多版本对齐而做类名/方法级 1:1 翻译映射。
- 多版本同步时强行对齐 L4 技术实现层。
- 将过程文件散落在课程目录中。
- 工业案例使用过期（>1.5年）数据或无来源量化指标。
- 演进路线起点档与主 Demo 代码不一致（套模板）。
- 未经视角 A-H 评估就宣称工作完成。
- 附录深入思考题跳过候选题→人工确认关卡直接写终稿。
- 深入思考题用基础知识题/定义题凑数（如"什么是 XX"）。
- 深入思考题给完整标准答案而非答题骨架。
- **实战课·应用架构特有反模式**：
  - 代码还没写完/指标还没达标就开始写讲义
  - 不Read真实代码，凭设计稿/记忆虚构类名方法名
  - 只讲"怎么做"不讲"为什么这么做、有什么trade-off"
  - 没有量化指标对比，用"效果显著提升"等模糊表述
  - 把架构课讲成"源码解读课"——逐行讲代码而非讲架构决策和演进
  - 过度设计：把生产级方案直接灌给学员，不解释"什么时候不需要这么复杂"
