# 架构案例写作规范 (Architecture Case Writing Guide)

本规范定义了**架构案例分析类长文档**的标准写作方法。风格基准为李智慧《大型网站技术架构：核心原理与案例分析》——平实直白、业务驱动、演进视角、全局权衡。

本规范是 `quality-guide.md` 的**高阶补充**：
- `quality-guide.md` 管底线——不能怎么做（去 AI 腔、禁角色卡、SVG 规范）
- 本规范管上限——架构类内容怎么写得有质感、有体系、像资深架构师在分享经验

适用于：实战课·应用架构的课程文档、架构案例分析书、技术架构深度文章等以架构设计为核心的长文档产出。

---

## 1. 核心写作哲学

所有写作手法的底层逻辑，都来自以下五条原则。写作时时刻对照，确保方向不偏。

### 1.1 业务驱动技术

驱动大型网站技术发展的主要力量是网站的业务发展。所有技术决策都从业务场景出发，而不是从技术先进性出发。

- 先讲业务是什么、业务遇到了什么问题，再讲技术怎么解决
- 技术选型的理由必须和业务约束挂钩（数据量级、时效性要求、团队规模等）
- 不说"这个技术很先进所以用它"，要说"业务遇到了 X 问题，这个技术刚好能解决"

### 1.2 演进而非设计

目前全球大型网站没有一个一开始规模就大的，都是从一台服务器开始慢慢发展出来的。架构是演化出来的，不是一开始就设计好的。

- 讲方案时优先按"演进路线"来讲——从最简单的方案开始，逐步升级，每一步解决前一步的问题
- 不假设一上来就用最复杂的方案，而是根据业务量级逐步引入复杂度
- 强调"在什么量级下用什么方案"，而不是"某某方案最好"

### 1.3 适度设计

反对为追求完美而过度设计。架构设计的目标是"够用、可靠、可演进"，而不是"技术上最完美"。

- 秒杀系统不需要绝对公平，适度公平即可
- 分布式事务不需要强一致，最终一致 + 对账兜底就够了
- 容量评估不需要精确到个位，数量级对 + 留有余地就行
- 每引入一个复杂度，都要有明确的收益，不能为了"高级"而加

### 1.4 分层治理

复杂问题不能指望某一层解决所有问题，要在链路的每一层都做处理，层层拦截、层层兜底。

- 秒杀系统的流量漏斗：CDN → 前端 → 应用 → 缓存 → 数据库，每一层挡一部分
- 幂等性的多层防御：前端防重 → 网关层 Token → 数据库唯一索引，一层失效下一层兜
- 故障处理的三层决策：止血 → 定位 → 长效改进，每一层解决不同阶段的问题

分层治理的核心思想是：**能在前面解决的，绝不往后传；能在内存中解决的，绝不打数据库；能异步的，绝不同步**。

### 1.5 兜底思维

在分布式环境下，任何方案都不能保证 100% 可靠。主方案负责 99.9% 的正常情况，兜底方案负责 0.1% 的异常情况，两者叠加才能达到 99.999% 的可靠性。

- MQ 延时消息是主方案，定时任务扫描是兜底方案
- 分布式锁是主方案，业务层幂等 + 对账是兜底方案
- 缓存是主方案，降级开关 + 数据库限流是兜底方案

写任何方案时，都要主动问一句：**"这个方案出问题了怎么办？"** 然后给出兜底手段。没有兜底的方案是不完整的。

## 2. 标准章节结构模板

每个架构案例章节，都遵循相同的结构模板。这不是死板的规定，而是经过验证的、最符合读者认知规律的叙事顺序。

### 2.1 标准五段式结构

```
## 第X章 XXXXX架构设计案例分析

（开篇引入：场景定义 + 为什么重要 + 本章路线图）

### X.1 技术挑战（或：XX的由来 / 为什么需要XX）
  - 先讲清楚这个问题是怎么来的、业务背景是什么
  - 分点列出核心挑战（3-5个为宜）
  - 每个挑战用具体数字或场景建立直观认识

### X.2 应对策略（或：XX方案对比与选型）
  - 对应挑战给出总体策略方向
  - 多个方案时用对比表呈现
  - 讲清楚每种方案的优缺点、适用场景、选型逻辑
  - 不是罗列方案，而是帮读者建立"怎么选"的判断框架

### X.3 架构设计（或：XX方案详解）
  - 深入到具体的架构设计和实现细节
  - 先给整体架构图/流程图，再逐层拆解
  - 关键技术点配代码示例或伪代码
  - 用演进路线的方式讲"为什么这么设计"

### X.4 治理与兜底（或：常见的坑与治理方案）
  - 主动讲方案的局限性和常见问题
  - 每个问题配对应的治理/兜底手段
  - 体现"没有完美方案，只有合适的方案 + 完善的兜底"

### X.5 小结
  - 提炼 3-5 条核心设计原则
  - 不是内容复述，而是上升到方法论层面
  - 可以关联其他章节（"这个思路在第X章也用到了"）
```

### 2.2 各段写法要点

**开篇引入**（每章开头 2-3 段）：
- 第一段：用定义式或场景假设式开头，让读者快速理解"这是什么"
- 第二段：讲清楚"为什么重要"——不解决这个问题会有什么后果
- 第三段：预告本章路线图——"本章我们从 X 讲起，然后看 Y，最后聊 Z"

**技术挑战段**：
- 用"具体来说"、"主要有以下几个方面"等自然过渡，不用"首先/其次"
- 每个挑战独立成一小段，先点出问题，再展开解释
- 尽量用"体感数字"量化问题（比如"10万人同时刷新，每秒几万请求"）

**方案对比段**：
- 方案数量 ≥3 个时，必须用对比表呈现核心维度
- 表格之后，每个方案再用 1-2 段展开讲原理和细节
- 最后必须有"选型建议"或"选型总结"——告诉读者"什么场景选什么"

**架构设计段**：
- 先文后图：先用文字描述整体架构，再放架构图（图文对应）
- 分层讲解：从上到下或从左到右，一层一层拆解开讲
- 重点深入：核心环节（比如库存扣减、消息发送）要讲透，非核心环节点到为止

**治理兜底段**：
- 用"坑"、"问题"、"局限性"等词汇切入，体现坦诚和务实
- 每个问题 → 对应一个解决方案 → 最好有真实案例支撑
- 这一段是区分"背方案"和"真懂"的关键——能主动讲问题的，才是真理解

**小结段**：
- 用"回顾本章的内容，核心设计原则可以总结为以下几点"开头
- 3-5 条原则，每条一句话概括 + 一两句话展开
- 原则要抽象、要能迁移——不只是"这个场景怎么做"，而是"这类问题怎么想"

### 2.3 方案对比表规范

方案对比表是架构案例写作中最常用的工具。用得好，读者一眼就能看明白各方案的差异和适用场景。

**维度选择原则**：

| 维度类型 | 说明 | 示例 |
|:---|:---|:---|
| **核心指标** | 方案最关键的性能/能力指标 | TPS、一致性级别、延迟 |
| **实现成本** | 接入难度、开发量、学习成本 | 业务侵入性：低/中/高 |
| **可靠性** | 出问题的概率和严重程度 | 高/中/低，或具体的兜底机制 |
| **适用场景** | 什么情况下选这个方案 | 日均<10万单、核心资金场景等 |

**表格写法要点**：
- 维度控制在 4-6 个，太多了读者记不住
- 第一列是方案名称，最后一列通常是"适用场景"（给读者决策依据）
- 表格里的文字要精炼，用短语不用长句
- 表格之后要有文字解读——把表格里的信息串起来，讲选型逻辑

## 3. 表达手法细则

### 3.1 数字量化原则

每个核心结论都要配一个"体感数字"。数字不必精确到个位，但数量级一定要对——它的作用是帮读者建立直观认识，而不是做精确计算。

**好的体感数字**：
- "Redis 单机就能支撑 10 万+ QPS，是数据库方案的几百倍"
- "秒杀活动峰值流量为日常峰值的 45 倍"
- "P99 从 2.1s 降到 380ms"
- "超卖了 20 件，20 个用户付款后无货"
- "单表数据量建议控制在 500 万 ~ 2000 万行"

**数字的三个来源（按优先级）**：
1. 工业界公开数据——大厂技术博客、技术大会分享、官方文档
2. 合理估算推导——基于已知参数推导（如"10 万人同时访问 200KB 页面 = 2GB 带宽"）
3. 经验性区间——行业公认的合理范围（如"单表 500 万 ~ 2000 万"）

> ⚠️ **硬约束**：数字必须有依据，禁止编造。如果找不到确切数字，用经验区间或定性描述代替，不能胡编一个精确数字。

### 3.2 开篇引入的三种句式

**定义式**：先给概念下定义，再展开。
> 秒杀是电子商务网站常见的一种营销手段：商家拿出少量热门商品，以极低的价格，在特定时间点开始销售，吸引大量用户抢购。

适用：读者可能不太熟悉的概念，或者需要先明确边界的场景。

**场景假设式**：用一个具体场景把读者带入，再引出技术问题。
> 假设某网站秒杀活动只推出 100 件商品，预计会吸引 10 万人参加活动，那么在秒杀开始的那一秒钟，可能会有数万个请求同时涌入系统。

适用：读者对场景有概念，但对量级和挑战没有直观认识的情况。用具体数字建立体感。

**业务价值式**：先讲业务上为什么需要这个东西，再讲技术。
> 网站通过这种营销手段，制造某种轰动效应，从而达到网站推广的目的。对于技术团队而言，秒杀是一场严峻的考验。

适用：技术同学容易忽略业务价值的场景，强调"技术是为业务服务的"。

实际写作中，这三种句式经常组合使用——先用定义式点题，再用场景假设式建立体感，最后用业务价值式升华。

### 3.3 问题提出与方案阐述句式

**问题提出**：
- "XX 系统需要面对的技术挑战有如下几点。"
- "除了上面提到的 XX，还有一些其他问题需要处理。"
- "事情没那么简单。"
- "这里有个容易踩坑的地方。"

**方案阐述**：
- "为了应对上述挑战，XX 的应对策略有如下几点。"
- "解决办法是使用 XX。"
- "办法是在 XX 加入 XX，在 XX 的时候才能得到。"
- "更彻底的方案是 XX。"

**过渡衔接**：
- "了解了挑战和策略，我们来看具体的架构设计。"
- "说到这里，自然会引出一个问题——"
- "这个方案看起来不错，但实际落地时也有一些坑。"

### 3.4 语言风格要求

- **平实直白**：像资深工程师在分享经验，不端着、不装逼。用"咱们来看"、"说白了"、"事情没那么简单"这种自然的表达
- **不堆砌术语**：能用大白话讲清楚的，就不用专业术语。必须用术语时，第一次出现要给解释
- **有温度但不煽情**：可以有个人判断和经验分享，但不要用"革命性的""里程碑式的"这种夸张词
- **就事论事**：讲技术就讲技术，不扯八卦、不吐槽、不打比方打得太远

### 3.5 禁用词补充

以下词汇在架构案例写作中**禁用**（和 `quality-guide.md §1.1` 的禁用词形成互补，以下为架构写作专项补充）：

| 禁用词 | 为什么禁用 | 替换建议 |
|:---|:---|:---|
| 首先 / 其次 / 再次 / 最后 | 机械感强，像提纲不像文章 | 用自然过渡，或用数字编号 + 小标题 |
| 综上所述 / 总而言之 | 八股味重，结尾无力 | 用"回顾本章的内容"、"说到底"等自然表达 |
| 不可或缺 / 至关重要 / 举足轻重 | 空洞，没有信息量 | 具体说清楚为什么重要——"没它会怎样" |
| 完美的解决方案 | 绝对化，不符合架构 trade-off 的本质 | "主流方案"、"常用方案"、"在 XX 场景下是合适的选择" |
| 革命性的 / 颠覆性的 | 夸大，不客观 | "生产级的"、"企业级的"、"被广泛采用的" |
| 业界公认 / 众所周知 | 模糊，没有依据 | 具体说——"XX 公司/团队在 XX 场景中采用了这种方案" |
| 不难看出 / 显而易见 | 对读者不友好，仿佛"看不懂就是你笨" | 直接讲结论和理由，不需要这种铺垫 |

## 4. 案例书生产流程

从一组场景题到一本完整的架构案例分析书，遵循以下六步流程。

### 4.1 Step 1：场景拆解

**目标**：明确这本书有几个场景、每个场景的核心问题是什么、它们之间是什么关系。

**产出**：场景清单 + 核心问题列表

**要点**：
- 每个场景用一句话概括核心问题（比如"秒杀系统——高并发下库存不超卖 + 系统不被打垮"）
- 识别场景之间的递进关系——是从易到难、从单点到系统、从技术到治理？
- 确定全书的主线——是按场景类型分章，还是按能力层级分章？

### 4.2 Step 2：案例调研

**目标**：为每个场景收集足够的工业界真实案例，作为写作素材。

**产出**：案例卡片集（每个场景 ≥3 个案例）

**案例卡片格式**：
```
## 案例卡片 N：公司名 — 场景名

- 公司/团队：
- 场景描述：
- 架构方案：（分点列出核心方案）
- 关键数据：（性能数据、规模数据、效果数据）
- 来源链接：
- 发布时间：
```

**调研要求**：
- 每个场景至少 3 个不同公司/团队的案例，交叉验证
- 优先选择有具体架构图、性能数据、故障复盘的案例
- 优先选择官方技术博客、技术大会分享等 P0/P1 级来源
- 注意案例新鲜度——架构原理类可以放宽，新兴技术优先近 2 年的

### 4.3 Step 3：大纲设计

**目标**：确定全书结构，分配知识点和案例到各章节。

**产出**：详细大纲（到二级或三级标题）

**要点**：
- 每章严格遵循"挑战 → 策略 → 架构 → 治理 → 小结"的五段式结构
- 案例要均匀分配——每章至少有 2-3 个真实案例穿插
- 数字要提前规划——每章有哪些核心数据、来自哪个案例，提前标注
- 章节之间要有递进关系，不要平铺直叙

### 4.4 Step 4：分章撰写

**目标**：按大纲逐章完成初稿。

**产出**：各章初稿（可以并行生产）

**要点**：
- 每章严格遵循结构模板（见 §2）
- 先把骨架搭起来（各级标题 + 每段核心观点），再填内容
- 案例和数据要标注来源，方便后续核查
- 写完一章后，自己先对照写作哲学 5 条过一遍，看看有没有偏离

### 4.5 Step 5：合并统稿

**目标**：把各章拼成完整的一本书，统一风格、术语、格式。

**产出**：完整初稿

**统稿检查清单**：
- [ ] 风格是否统一——各章的语气、节奏、表达方式是否一致
- [ ] 术语是否统一——同一概念前后叫法是否一致（比如"最终一致"还是"最终一致性"）
- [ ] 衔接是否流畅——章节之间的过渡是否自然
- [ ] 案例是否重复——同一个案例是否在多章重复出现且角度雷同
- [ ] 数字是否一致——同一数据前后是否一致（比如前面说"10万QPS"后面说"几万QPS"）
- [ ] 深度是否均衡——各章的信息量和难度是否匹配

### 4.6 Step 6：质量审查

**目标**：确保最终产出符合所有质量标准。

**产出**：终稿 + 审查记录

**审查清单**：
- [ ] **AI 腔扫描**：全文搜索禁用词，确认零残留
- [ ] **结构完整性**：每章是否都有完整的五段式结构
- [ ] **数字量化**：每个核心结论是否都有体感数字支撑
- [ ] **案例可靠性**：所有案例数据是否有来源标注，来源是否可信
- [ ] **兜底思维**：每个方案是否都讲了局限性和兜底手段
- [ ] **业务驱动**：技术决策是否都有业务约束和选型理由
- [ ] **小结质量**：每章小结是否提炼了原则，而非内容复述

## 5. 常见误区

### 误区一：把书写成了技术词典

把各种技术方案罗列一遍，每个方案讲一下原理，就完了。这不是案例分析，这是技术词典。

**正确做法**：从业务场景出发，先讲问题，再讲为什么需要这个技术、这个技术解决了什么问题、还有什么问题没解决、怎么兜底。技术是手段，不是目的。

### 误区二：只有方案，没有权衡

只讲"某某方案怎么好"，不讲它的代价和局限性。这是典型的"背题式"写法——知道方案，但不理解 trade-off。

**正确做法**：每个方案都要讲清楚它的优点、缺点、适用场景。讲选型的时候，说清楚"在什么约束下选什么方案"，而不是"某某方案最好"。

### 误区三：没有案例，全是理论

通篇都是理论和原理，没有一个真实案例。读者看完了知道"是什么"，但不知道"在真实项目里怎么用"。

**正确做法**：每个核心观点都要有真实案例支撑。案例不用太长，一两段话 + 几个关键数据就行，但必须是真实的、有来源的。

### 误区四：结构混乱，想到哪写到哪

章节之间没有逻辑关系，每章内部结构也不统一，读者看完脑子里是一团浆糊。

**正确做法**：严格遵循标准结构模板。模板不是束缚，而是帮你把内容组织得清晰有序。读者不用费脑猜你接下来要讲什么，顺着结构走就行。

### 误区五：语言太学术或太油腻

要么像论文一样晦涩难懂，要么像营销文案一样浮夸油腻。两种极端都不可取。

**正确做法**：平实直白、像前辈分享经验的口吻。用大白话讲清楚复杂问题，才是真水平。
