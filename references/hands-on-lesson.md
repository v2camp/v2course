# 入门实战三段式规格（实战课·入门实战）

> 适用范围：**实战课·入门实战**（原「实战课·基础/实战」）的讲义与课程文档。
> 与 `templates.md §3.2` 配套——**骨架与课堂节奏看 `templates.md §3.2`，每段内部的内容规格看本文件**。
> 工程组织（basic/full 双 app、starter tag、DoD 红线）见 `multi-track-production.md §5`。

---

## 0. 为什么是三段

入门实战课有两种典型失败形态：

- **只讲不练**：概念讲透、演示跑通，学员看会了但自己写不出来；
- **只练不讲**：跟着讲师抄完 3-4 个文件，跑通了，但不知道每个决策从哪来，换个项目就废。

三段式把一节课切成**认知 → 理解 → 产出**三步，分别对应「这个领域用什么零件」「预置代码为什么这么切」「我怎么自己把它做出来」。三段缺一，basic 就只是抄出来的产物，不是学员自己的能力。

---

## 1. 三段式总纲

| 段 | 回答的问题 | 学员下课带走 | 课上时长 |
|:---|:---|:---|:---|
| **① 组件学习** | 这个领域用什么零件、什么套路 | 可复用的组件认知 + 一套术语 | 12 min |
| **② 代码讲解** | starter 预置的代码为什么这么切 | 能读懂 starter 的设计理由 | 10 min |
| **③ 实战开发** | 我怎么自己把它做出来 | 跑通的 basic + 2 张课后任务卡 | 35 min（课上）＋ 课后 |

> 三段**替换**的是旧骨架里「整体设计 + 代码结构导览 + 现场构建」的内容规格，**不是**删掉现场构建。现场构建仍是课上主体，见 §4.1。

## 2. 段一 · 组件学习

### 2.1 三层组件（讲的时候分层，不要混在一张嘴里）

| 层 | 是什么 | 例（TS 轨） |
|:---|:---|:---|
| **基础组件** | 框架/库的核心抽象 | LangGraph.js 的 State / Node / Edge、Annotation、Checkpoint |
| **设计模式** | 组件之上的固定套路 | 主管-执行者（Supervisor/Worker）、模板方法 + LLM 优先失败兜底、契约先行 |
| **架构模式** | 跨组件的装配方式 | 线性链 → 状态机 → 图编排；无隔离 → `tenant_id` 过滤 → RLS |

### 2.2 讲什么：三问筛选（**全 Yes 才进段一**）

1. **首次出现问**：该组件/模式在本课是否首次出现？不是 → 放附录或延伸阅读，不占正课时间。
2. **决策依赖问**：不懂它，现场构建那 3-4 个关键文件的决策就讲不通吗？不是 → 降级为一句带过。
3. **可迁移问**：换个项目学员还能用上吗？只是本 Demo 的实现细节 → 不进（留给代码讲解）。

### 2.3 怎么讲

- **先失败后组件**：先给「没有它会翻什么车」的失败现场，再引出组件本身。上来就报零件名等于背说明书。
- **一个组件只讲一组核心抽象**（≤3 个），配一张图。
- **术语首现即释**（`quality-guide.md`、architecture-narrative 病灶四）。
- **禁止**组件说明书式罗列：枚举全部 API / 配置项是文档的事，不是课的事。

### 2.4 配图：三类保底图

每节入门实战课**至少三张**矢量图，缺一即不达标。三类图的**内容规格、命名与规则唯一定义**在 `diagram-integration.md §6.1`，此处只点明本课型要哪三类：

- **组件图**（`architecture`）——本课引入的基础组件及其关系
- **模式图**（`sequence` / `flow`）——本课所用设计模式/架构模式的一次完整运转
- **骨架图**（`architecture`）——本课 basic 的整体骨架（谁调谁、数据从哪进从哪出）

> 一图只表达一种主关系，不要把组件与流程混在一张图里（`diagram-integration.md §2`）。

## 3. 段二 · 代码讲解

讲 **starter 预置的那部分代码**——现场写的文件在 §4.1 的四拍里带决策讲，这里不重复。

### 3.1 讲什么

| 内容 | 要讲出的东西 |
|:---|:---|
| **类型契约** | 字段为什么这么定、边界在哪、谁写谁读、为什么放共享层而不是就地造 |
| **mock 数据** | 为什么切这么大（够跑通主动线的最小集）、真数据什么时候接管 |
| **目录与分层** | 每层职责边界、为什么是这几层 |
| **预置 vs 现场写** | 哪些已预置、哪些留给学员、分界理由 |

### 3.2 怎么讲

- **沿数据流 / 调用链讲，不沿目录树讲**（目录树巡览是反模式，见 `anti-patterns.md`）。
- 每个文件给三句话：**职责** + **为什么此刻存在** + **学员要不要动它**。
- **只列 basic 内文件**；全工程索引出列即违规。

## 4. 段三 · 实战开发

### 4.1 课上：现场构建四拍（保留，不变）

3-4 个关键决策文件，每步四拍：**写什么 → 为什么这么写 → 跑一下 → 看到了什么**。
沿用 `templates.md §3.2` 的两条硬约束：

- **预置 / 现场写分界**：脚手架、完整类型契约、mock 数据、smoke 样例预置；组合逻辑、主流程、编排连线现场写。
- **每步「跑一下」须在该步文件状态下可执行**：禁止引用仍是空壳或尚未接线的文件；把「跑整条主命令」排在最后一个文件写完的收尾步。

### 4.2 课后：实战任务卡 ×2

任务卡是**学员自驱**的实战单元：给定起点与提示词，交给 harness（AI 编码工具）生成代码，按完成判据自检，与对照答案比对。它与课上四拍是**分工**关系——四拍练「从零构建的决策过程」，任务卡练「把需求说清楚 + 审 AI 产出的 vibe coding 能力」。

#### 4.2.1 任务选题三问（**全 Yes 才收**）

1. **演进锚点问**：它是 basic → full 演进路径上的一个真实小增量吗？——做完的产物能被下一节架构课接住。
2. **独立可跑问**：在 basic 完成态上能独立跑通验收吗？不必先补齐其他未讲内容。
3. **vibe 值问**：它能练到「把需求说清楚 + 审 AI 产出」吗？不是单纯打字练习。

> 两类合规来源：① **演进路径上的小任务**（首选，例如给 4 节点线性链加一个 `validateSql` 节点与失败回环）；② **提升 vibe coding 水平的任务**（例如「给这段加一层失败兜底并写测试」），须写明练的是什么。
> **不合规**：与演进线无关的独立小玩具；把课上四拍换个说法重抄一遍。

#### 4.2.2 任务卡模板（八要素，缺项即不达标）

````markdown
### 任务 N：<一句话目标>

- **起点**：checkout <tag>，从 <文件> 开始
- **背景**：<2-3 句，说明它在 basic→full 演进线上的位置>
- **提示词（可直接复制）**：

  ```text
  <提示词全文>
  ```

- **完成判据**：跑 `<命令>`，应当看到 <具体输出>
- **不许改**：<文件清单>（改了会破坏 starter 契约）
- **对照答案**：<full / basic 完成态里的文件路径>
- **自检三问**：<问题 1 / 2 / 3>
- **验证方式**：<静态推演 ｜ 实跑>（注明验证时间与结论）
````

#### 4.2.3 提示词六要素

| # | 要素 | 要求 |
|:---|:---|:---|
| 1 | **上下文** | 工程路径 + 起点文件 + 现有契约名（须与真实代码一致） |
| 2 | **目标** | 一句话、可验收的结果 |
| 3 | **约束** | 不许改的文件清单、不许引入的新依赖、代码量上限 |
| 4 | **判据** | 跑什么命令、看到什么输出 |
| 5 | **风格** | 沿用既有命名 / 分层 / 错误处理惯例 |
| 6 | **自检** | 要求 harness 输出它改了哪些文件、为什么这么改 |

#### 4.2.4 硬性要求

- 提示词**不依赖课堂上下文**：学员课后单看就能跑，不引用「刚才讲的」。
- 完成判据**必须可观测**（命令 + 具体输出），禁止「实现得差不多」「基本可用」。
- **「不许改」清单必填**——防 harness 把 starter 契约改崩。
- **验证方式必填且如实**：未实跑就写「静态推演」，不得谎称实测（仓库既有红线）。
- 每节入门实战课 **2 张左右**（1-3 张可接受），不堆量。

## 5. 过渡契约（入门课 → 架构课）

同一组内，入门实战课与架构课之间必须有**双向勾稽的过渡契约**：

| 方向 | 要求 |
|:---|:---|
| **入门课 → 架构课** | 入门课第六段「架构课往上加什么」预告的每个增强点，架构课必须有一处对应的 basic→full 锚点（不要求同名，须同义） |
| **架构课 → 入门课** | 架构课开场引用的 basic 痛点，必须是入门课真正留下的问题（不得凭空造痛点） |
| **任务卡 → 架构课** | 任务卡的产物是学员自带的「半步 full」，架构课可显式承接（可写「如果你做了任务 2，这里你会认出它」） |

**验收方式**：做一张两向对照表（预告项 ↔ 锚点），记入 `phase-4 sync-record`；Phase 5 视角 D/E 复核。任一侧有孤儿项即退回。

> **组内「1+2」形态**（如本课是组内唯一入门课、前一门是旧口径课）：入门课开头须有一段**结构切换说明**，交代与前序课的形态差异和工程起点，否则学员会以为走错教室。

> **跨区间换题同理**：多区间系列（如 9-12 旅游多 Agent → 13-16 店掌柜 → 17-20 多租户平台）的新区间**第一课**，正文开头（课前准备之后、需求开场之前）须有一小节交代三件事：① **为什么换题**——上一区间答错只是体验问题、新场景答错是账实不符，哪条约束变硬了；② **本课在链上哪一环**——本区间四课各承担什么，本课交付哪一段；③ **复用上一区间什么**——契约先行 / LLM 优先失败兜底 / 节点留痕等可迁移方法（换题不换方法）。
>
> 反例：某课作为新区间首课，从上一课直接跳到"先把整条链的终点摆出来"，学员第 8 分钟就要跑命令，动机全靠讲师口头补；全课只有一行「实战3」标签。
