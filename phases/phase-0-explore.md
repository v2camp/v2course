# Phase 0 — Explore & Challenge（开放探索与互相质疑）

## 目标

把内容方向与交付标准讨论透，而不是一上来写稿。

## 必谈七件事

1. **课程时长确认**：本次内容的预计时长是多少（如 90 分钟、2 小时）？（通常可从先导/规划材料中提取）。
2. **命名与结构规范**：
   - 产物目录的命名规范是什么？
   - 大纲、讲义、代码目录的具体命名方式（请用户提供一份**示例**）。
3. **多版本识别**：是否涉及多版本（如 TS 版、Java 版）？
   - L1 产品体验（标题/主张/场景/Demo效果/handoff）、L2 架构逻辑（演进档位/失败模式/拓扑/三域）、L3 工艺规范（SVG/标签/排版/论据）必须一致
   - L4 技术实现（类/方法/API/框架/配置）各自独立，不做类名级映射
4. **内容定位**：核心作用（破题、习得、叙事）是什么？
5. **主案例/核心论据**：最适合用哪个案例承载主线？
6. **表达/演示形态**：live coding、预制 demo、PPT 汇报等。
7. **架构演进位置**（系列实战课必填）：本课在系列课程的架构演进中处于哪个阶段？
   - 起点档（如 S0 单点原型）？中间档？收尾档？
   - 本课主 Demo 实际实现到 S0-S4 的哪一档？（基于代码而非讲义草稿判断）
   - 本课架构的"上一形态"（前序课实现了什么）和"下一形态"（后续课往哪演进）？
   - 技术栈与领域声明：本课使用的语言/框架是什么？所属技术领域是什么？需参照 `references/domain-adaptation.md` 完成领域适配声明（三域命名、S0-S4映射、主要信源站点等）。

## 必须怎么做

- **先提出 2-3 个可行方向**，说明各自 trade-off。
- **强制确认命名**：在用户未给出/确认命名示例前，不得猜测目录结构。
- **主动质疑时长**：评估在预定时间内，当前计划的内容是否会过载或过轻。
- **过程文件归档**：将本阶段产出存入项目根目录 `.course/{task_name}/phase-0/`。

## 本阶段产出（必须）

- `内容定位卡` (含确认的时长与版本信息)
- `交付物命名规范说明` (基于用户示例)
- `多版本 L1-L3 共性/L4 特性划分表` (若适用)
- `主案例候选清单`
- `表达/演示形态判断`
- `架构演进位置卡`（系列实战课，含起点档确认与前后课 handoff）

## 退出条件

- 用户已确认方向与时长。
- 用户已提供/确认命名示例。
- 已区分多版本 L1-L4 差异点（若适用）。
- 已记录"为什么不选另外两个方向"。
- 系列实战课已确认演进位置（S几）和主 Demo 起点档。
