# Phase 4 — Consistency Sync（一致性对齐）

> **说明**：本阶段面向**已存在**的平行版本做对齐。若是从单一源头**净新建**第二/第三技术栈（如 V3 只有 Java 版、需派生 TS 版），走 `references/multi-track-production.md` 的"双轨净新建"路径（契约映射表先行 → 反向派生），本阶段 L0-L4 仅供派生后校验用。

## 目标

确保演示代码、配置环境、事实论据与本课型的核心产物之间保持 100% 一致，同时确保各产物之间的结构一致性。
（产物因课型而异：公开课为大纲/讲义/课程文档；**实战课为讲义/课程文档，无大纲**；录播课另含 PPT文稿/录制脚本。）

## 触发条件

- 演示项目代码发生实质性变更。
- 外部依赖或技术架构调整。
- 事实论据或行业标准发生更新。
- 辅导类：目标职级标准或岗位要求发生变化。

## 对齐清单（L0-L4 分层）

### L0 版本独立红线层（多版本必检）

多版本课程（如 TS 版 + Java 版）下，各版本**独立成篇、互不侵入**，这是与 L1-L3"对齐"相反的约束，二者同时成立：

- [ ] **零跨版本对比表述** — 全稿不得出现"与 X 版相比 / X 版用 Y / 另一版本 / 双轨"等对比性表述
- [ ] **零他栈技术名词残留** — 不得残留源栈品牌名、API 名、依赖（如 TS 版残留 Java 版 Spring 术语，或 Java 版残留 LangGraph.js）
- [ ] **红线扫描 0 命中** — 用关键词扫描（各版本禁用词 + 对比连词 + 他栈技术名）全量过一遍，逐版本 0 命中
- [ ] **附录独立完整** — 各版本附录清单（A/B/C…）与自身正文条目数对应，不因"对齐"而从他版拷贝缺失附录

> **核心原则**：学员在不同版本里学到的架构认知和工程判断力应一样，但两个版本的**文档资产本身各自完整可独立存在**，不存在"主版本 + 副本"。L0 独立红线与 L1-L3 结构对齐是两条正交的约束，都须通过。

### L1 产品体验层（必须对齐）
- [ ] **标题/主张对齐** — 课时标题、一句话主张、目标受众在各版本中是否一致？
- [ ] **场景/Demo对齐** — 问题场景、Demo 最终效果（学员完成后得到的作品体验）是否一致？
- [ ] **handoff 对齐** — 价值落点、后续课程衔接是否一致？

### L2 架构逻辑层（必须对齐）
- [ ] **演进档位对齐** — 演进路线的档位划分（S0-S4）是否一致？（允许合并档位但不能缺失核心阶段）
- [ ] **失败模式对齐** — 失败模式的核心问题（根因）是否一致？（表现描述可不同）
- [ ] **拓扑对齐** — 数据流拓扑（节点和边的关系）是否一致？
- [ ] **三域对齐** — 三域划分（控制流/能力/交互的分配）是否一致？

### L3 工艺规范层（必须对齐）
- [ ] **图对齐** — `images/` 图数量与语义是否对齐（archsvg 渲染；双轨走 `variant_parity` 校验），具体布局由 archsvg 决定
- [ ] **标签对齐** — 干货标签（【知识点】/【要点】/【敲黑板】）位置和承载的内容是否一致？
- [ ] **排版/论据对齐** — 表格、排版、术语统一度、事实论据/数据引用是否一致？
- [ ] **附录思考题对齐** — 深入思考题数量、题型分类（架构题/深度题配比）、格式结构是否一致？（每道题的具体选题和答案深度可因技术栈特性略有差异：Java 栈选更贴合 Java 生态的题，TS 栈选更贴合 TS/Node 生态的题，但必须保证每题都通过三质量维度检查）

### L4 技术实现层（各自独立，不强制对齐）
- [ ] 类名、方法名、接口签名 → 各版本独立
- [ ] 框架选型、库依赖 → 各版本独立（写各自技术栈最地道的实现）
- [ ] 配置写法、环境变量名 → 各版本独立（只要求 .env.example 覆盖的变量一致）
- [ ] 代码行数/文件结构 → 各版本独立

> **核心原则**：学员在不同版本里学到的架构认知和工程判断力是一样的，
> 但写出的代码看起来应该像"该技术栈最地道的写法"，而不是"另一个技术栈的翻译腔"。
> 禁止为了"对齐"而做类名/方法级的 1:1 翻译式映射。

### 产物结构一致性（各课型必检）

本课型各产物的章节/分段结构必须 1:1 对应，这是链式生产的基本要求。
参检产物：**公开课** = 大纲/讲义/课程文档；**实战课** = 讲义/课程文档（无大纲）；**录播课** = 大纲/讲义/课程文档/PPT文稿/录制脚本。

- [ ] **标题层级对齐** — 上游产物（公开课/录播课为大纲，**实战课为 Phase 1 主线结构**）的 H2/H3 层级是否与下游完全一致？
- [ ] **标题时间标记拉齐** — 标题中的时间标记（如 `（15min）`）**讲义保留、课程文档/大纲必须剔除**；检查时一律先把时间标记剥除后再比对标题正文，防止"一处删了、一处没删"的漂移。
- [ ] **章节顺序一致** — 各章节的排列顺序是否完全相同？
- [ ] **章节数量一致** — 有没有某个产物多了或少了章节？
- [ ] **核心内容对应** — 上游产物中的每个核心要点，在下游产物中是否都有展开？
- [ ] **附录对齐** — 附录（思考题、来源清单等）在各产物中是否都存在且对应？**索引类附录（挖坑索引表、代码索引表）须对照正文实际条目数核对一致，缺则补齐。**

> **注意**：结构一致不代表内容完全一样——讲义有讲师口播和演示动作，课程文档有书面化表达，这是正常的。但**章节标题、章节顺序、章节数量**必须 1:1 对应。

### 代码/演示对齐（通用检查项）
- [ ] **代码/演示对齐** — 文稿中所有代码示例、操作步骤、界面描述是否与实际 Demo 一致？
- [ ] **环境/配置对齐** — README、`.env.example` 等配置说明是否与实际执行环境一致？
- [ ] **论据/事实对齐** — 引用的数据、链接、发布时间是否为最新？是否有残留的过期引用？
- [ ] **演进起点对齐** — 讲义中"本课实现了什么"是否与主 Demo 代码一致？
- [ ] **跨课时 handoff 对齐** — 本课声称"下一节课讲 X"是否与下一课的主线结构/大纲一致？前后课演进档位是否连贯不矛盾？

## 对齐原则

- **事实优先，文稿反向适配** — 先确定 Demo 代码或行业事实的最终形态，再同步修改文档。
- **修改范围最小化** — 只修改过时或冲突的部分。
- **L4 不强行对齐** — 技术实现层差异不是"问题"，是各版本独立的正常状态。
- **变更理由可记录** — 若涉及重大逻辑调整，需在 `.course/{task_name}/phase-4/` 记录理由。

## 本阶段产出

- 更新后的核心产物（本课型的产物，如公开课的 `大纲.md` / `讲义.md` / `课程文档.md`；实战课无大纲）。
- `.course/{task_name}/phase-4/sync-record.md` 对齐记录（按 L1-L4 分层记录 + 产物结构一致性检查记录）。路径规则：若有项目目录则在项目根目录下，否则在当前工作目录下。

## sync-record.md 模板

```markdown
## L1-L3 对齐项
| 对齐维度 | {版本A}位置 | {版本B}位置 | 对齐方式 |
|:---|:---|:---|:---|
| 一句话主张 | §一 | §一 | 相同 |
| P2 多源融合拓扑 | §7.3 图2 | §7.3 图2 | 图含义一致（archsvg 渲染，跨版本语义对齐） |

## L4 独立实现说明
| 维度 | {版本A} | {版本B} | 差异理由 |
|:---|:---|:---|:---|
| HTTP 客户端 | fetch 原生 | RestClient | 各自生态标准 |
| 状态管理 | Annotation.Root + reducer | OverAllState + ReplaceStrategy | 框架原生机制不同 |
```

## 退出条件

- **（多版本）L0 版本独立红线通过**：跨版本对比表述 0、他栈技术名词残留 0、红线扫描 0 命中。
- L1-L3 对齐清单全部勾选。
- L4 独立实现差异已记录（非对齐项）。
- 三产物结构一致性检查通过（标题层级/时间标记拉齐/章节顺序/章节数量/附录对齐 1:1 对应）。
- 无过期引用残留。
- 演进起点与主 Demo 代码一致，跨课时 handoff 连贯。
- 用户确认对齐完成。
