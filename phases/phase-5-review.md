# Phase 5 — Review & Finalize（综合评估与定稿）

## 目标

通过多重视角评估（六视角（运营+学员+代码+演进路线+深入思考题+代码引用/飞书兼容））及专家独立审查，确保内容彻底戒除 AI 腔、提供极致的视觉美感与多维价值，达到 卓越品质标准。

---

## 1. 六视角综合评估 (MANDATORY)

在专家审查前，主 Agent 必须完成以下自我评估。如果某项不合规，必须返回 Phase 3 修正。

### 视角 A：流量运营与转换视角
- **吸睛度与张力**：开篇是否在 10 秒内抓住注意力？痛点引入是否有强烈的冲突和窒息感？
- **转换/桥接**：CTA（行动号召）是否自然且强力？本课如何与后续课时无缝桥接，避免孤岛化？

### 视角 B：内容可行性与工程细节
- **可行性与自检**：文中的代码、命令是否真实可靠？是否正确使用 **【敲黑板】** 标出可能踩坑的环境、代理、依赖问题？是否给出了成功执行的控制台自检日志？
- **密度评估**：内容量是否匹配预设**课程时长**？

### 视角 C：深度技术架构
- **技术深度与本质**：是否正确使用 **【知识点】** 承载和挖掘深度的底层原理、设计思想？这些内容是否具有架构师级的深度与洞察力（而非初级 API 堆叠）？
- **无夸大包装**：是否清除了所有浮夸的角色特定修饰语（如"神级背诵版"、"吊打面试官"）？

### 视角 D：演进路线专项（系列实战课必检）
- **案例新鲜度**：工业案例发布时间是否 ≤1.5 年？是否填写了新鲜度自检表？
- **起点对齐**：本课讲义中"起点档"描述是否与主 Demo 代码实际实现一致？
- **SVG 完整性**：演进路线总图（evolution-roadmap.svg）是否存在？每档是否至少 1 张 SVG 且引用路径正确？
- **数据溯源**：所有量化指标是否标注了来源（公司 + eval 规模 + 时间）？
- **跨课时连贯**：handoff 到下一课的内容是否与下一课大纲一致？前后档位不矛盾？
- **失败模式真实性**：3 类失败模式是否基于本课主 Demo 实际短板，而非套模板？

### 视角 E：附录深入思考题专项（实战课必检）
质量维度定义见 `references/interview-questions.md` §2。对附录中每道题逐条检查：
- **E1 知识结构**：答案是否需要分层面/分维度组织（≥2 维度），不是单点背诵题？
- **E2 紧扣超纲**：题干是否锚定了本课 Demo 具体元素，且问题指向正文未覆盖的深度/广度？
- **E3 trade-off**：是否没有唯一答案，至少明确 2 个权衡维度？
- **E4 追问链**：是否有 2 层追问，且追问层层深入（不是平行问题）？
- **E5 答题骨架**：是否有核心思路 + 关键权衡 + 延伸方向三层？
- **E6 关联阅读**：是否每道题至少 1 条工业界真实来源链接？
- **E7 非基础题**：是否不是"什么是 XX"这类定义题？
- **E8 题型配比**：默认 3 架构题 + 1 深度题（题数有调整时，架构题占比 ≥ 60%）？
- **E9 篇幅控制**：4 道题总篇幅是否 ≤ 讲义总篇幅 15%？
- **E10 不给完整答案**：是否只有答题骨架，没有逐字标准答案？

### 视角 F：代码引用与飞书兼容专项（应用架构课必检）
> 仅实战课·应用架构类型需要检查。基础/实战课跳过此视角。

规范定义见 `references/code-reference-feishu.md`。逐条检查：

- **F1 零 file:// 链接**：全文不得有任何 `file://` 开头的链接，不得有本地绝对路径的 Markdown 链接
- **F2 类名行内代码格式**：所有引用的类名均使用行内代码格式（`` `ClassName` ``），确保学员可复制搜索
- **F3 首次出现带路径**：每个类首次出现时带有包路径简写（括号内标注）
- **F4 包路径简写无歧义**：简写后的包路径能唯一识别到包，不会与其他包混淆
- **F5 核心代码索引表存在**：每讲末尾有「本讲核心代码索引」表格
- **F6 索引表完整性**：索引表包含本讲正文提到的所有核心类，无遗漏
- **F7 索引表准确性**：表中的类名、相对路径与真实代码 100% 一致（先 Read 代码再写表）
- **F8 系列首讲有前置说明**：应用架构系列课第一节课开头有代码根目录、路径约定、学习方式说明
- **F9 代码片段带路径注释**：展示的代码块第一行有 `// 文件：相对路径` 注释
- **F10 无过度代码搬运**：代码片段均为 10-30 行核心逻辑，没有整文件贴代码的情况

## 2. 审查角色与分工

| Subagent | 审查维度 | 不审查 |
|:---|:---|:---|
| **技术布道师** | 技术准确性、代码可运行性、配置一致性、技术选型理由、深入思考题关联阅读来源真实性、**代码引用准确性（类名/路径与真实代码对不对得上）** | 叙事、案例叙述、价值表达、去 AI 味 |
| **代码审查专家** | 代码本身的技术质量（按本次声明的技术栈审查） | 讲义内容、课程设计、表达风格 |
| **表达教练** | 措辞去 AI 腔（工程口语拟真）、叙事张力与痛点公式、扁平化干货排版规范（禁用卡片/高亮中立词）、独立 SVG 图像及视觉规范、演进路线表达质量、深入思考题表达质量（场景锚定/追问链深度/答题骨架清晰度）、**飞书兼容性（file://链接清零、代码索引表规范）** | 详细技术细节、具体代码语法 |

> **技术布道师 vs 代码审查专家的区别**：
> - 技术布道师 = "讲义里写的代码和实际代码对不对得上"（文档侧）
> - 代码审查专家 = "代码本身写得好不好、有没有 bug、架构合不合理"（代码侧）
> - 两者互补，缺一不可

> **飞书兼容性审查分工**：
> - 表达教练负责：检查是否有 file:// 链接、索引表格式是否规范、排版是否符合飞书兼容要求
> - 技术布道师负责：检查类名/路径是否与真实代码一致、包路径简写是否准确

## 3. 执行步骤

### Step 1：主 Agent 专项质量自评
- 结合以下参考文件对核心文稿进行逐段扫描：
  - 品质规范参考 `references/quality-guide.md`
  - 演进路线参考 `references/evolution-roadmap.md`
  - 深入思考题参考 `references/interview-questions.md`
  - 代码引用/飞书兼容参考 `references/code-reference-feishu.md`
- 产出 `.course/{task_name}/phase-5/evaluation-summary.md`，重点审计：
  - 是否存在禁用词（首先/其次/综上所述等）？
  - **情绪张力是否绝对基于真实案例？（严禁凭空捏造）**
  - **是否彻底清除了三大卡片组件（讲师/学员/面试卡）与浮夸词汇？**
  - **是否规范使用【要点】、【知识点】、【敲黑板】承载核心干货？**
  - 是否无 ASCII 图，且 SVG 图引用无误？
  - **演进路线案例新鲜度是否 ≤1.5 年？起点档是否与主 Demo 代码一致？**
  - **附录深入思考题是否通过 E1-E10 全部检查项？（若本课包含附录）**
  - **（应用架构课）代码引用与飞书兼容性是否通过 F1-F10 全部检查项？**

### Step 2：并行启动专家审查
启动表达教练、技术布道师、代码审查专家 subagents，分析产出：
- `.course/{task_name}/phase-5/expression-review-report.md`
- `.course/{task_name}/phase-5/tech-review-report.md`
- `.course/{task_name}/phase-5/code-review-report.md`

**应用架构课额外要求**：
- 技术布道师报告必须包含「代码引用准确性」专项检查结果
- 表达教练报告必须包含「飞书兼容性」专项检查结果

### Step 3：汇总与改进
- 如果自评或任何专家报告显示"不合格"或存在 🔴 项，必须返回对应 Phase 进行改进。
