# Phase 2 — Build the Evidence System（构建证据/案例系统）

## 目标

让案例与证据真正服务于核心主张，避免堆砌无关材料。

## 双轨并行规则

### A. 经验线（优先）

优先级如下：
1. **亲历案例/成果**（如：我带过的项目、我解决过的 Bug、我的晋升项目）
2. **观察/见闻/复盘**（如：团队发生的冲突、看到的面试题、行业内卷现状）
3. **公开案例**

经验线的用途：
- 调动受众情绪，建立代入感。
- 建立真实感，体现"我做过"或"我见过"。
- 提供叙事张力、冲突感和个人能力亮点。

允许表达：
- 可以保留模糊性以保护隐私。
- 可以侧重于过程描述。
- 辅导类：重点展示"在压力/挑战下的决策过程"。

### B. 事实线（必需但从属）

公开案例、论文、行业报告、官方文档、架构标准、财报、权威数据，主要负责：
- 支撑确定性判断。
- 限定结论边界，防止过度外推。
- 在汇报/讲义中提供可追溯的权威依据。

硬规则：
- 只要涉及**事实性判断、行业结论、架构模式、度量数据**，就必须有可靠支撑。
- 每个事实点需保留：来源名称、原始链接/出处、时间口径、在本次内容中的使用语境、风险提示。
- 辅导类：事实线应包含"职级评审标准"或"JD 核心要求"。

### B.3 演进线证据（系列实战课必需）

当 Phase 1 决定本课包含"架构演进路线图"收口段时，必须在事实线中单独采集演进证据。

#### 调研通道（强制）

agent-reach 的 `web` / `dev` / `search` 三分类用法与降级说明，**唯一定义**见 `references/evolution-roadmap.md` §3.4，此处不复述。本阶段只规定检索动作：

1. 一线工程博客（Anthropic / Netflix / Uber / Meta / ByteDance / Google / LinkedIn / Slack / meituan / alibaba / tencent 等 Engineering Blog）
2. GitHub 开源项目的 RFC / Architecture Decision Record
3. 顶级会议分享、技术白皮书（补充）

关键词策略：
- 通用模板：`{领域} architecture evolution production case study`
- 短板反推：基于本课起点档（S0）的实际失败模式，反推下一档关键词
  （例：若 S0 瓶颈是"串行执行慢" → 搜 `parallel {领域} production architecture`）

#### 采集硬约束

三条硬约束（**新鲜度 / 真实度 / 量化指标**）的唯一定义与阈值见 `references/evolution-roadmap.md` §3.1/3.2，此处不复述——改阈值只改那边。本阶段额外加一条：

- **架构可引用**：有公开的架构拓扑图或设计文档

#### 必采字段

| 字段 | 说明 |
|:---|:---|
| 案例名 | 公司/团队 + 系统名 |
| 来源 URL | 原始链接（非二手转述） |
| 发布时间 | YYYY-MM，用于新鲜度校验 |
| 工业应用证明 | 用户规模/请求量/业务场景 |
| 量化指标 | ≥3 项 |
| 演进驱动力 | 为什么从 N 档演进到 N+1 档的真实瓶颈 |
| 使用语境 | 在本课哪个档位引用 |

#### 起点档验证

采集演进证据前，必须先确认：
- 本课主 Demo 实际实现到了 S0-S4 的哪一档？
- 禁止硬套通用模板，把已实现的形态标为"未实现"。
- 若主 Demo 已合并多档（如直接用 Plan-Execute），起点档合并记录。

### C. 深入思考题候选题（实战课必需）

当 Phase 1 决定本课包含"附录深入思考题"时，必须在证据采集完成后产出候选题卡片。

方法论详见 `references/interview-questions.md`。

#### 候选题产出目标

- 总量：8-10 张候选卡片
- 配比：主路径 C（架构题，约 6-7 道）+ 辅路径 A（深度题，约 2-3 道），最终由用户选 4 道
- 质量门槛：每张卡片必须逐条勾选三质量维度（知识结构/紧扣超纲/trade-off），不满足的不输出

#### 主路径 C：本课 Demo 架构 → 向上推演（架构题来源）

执行步骤：
1. 基于演进路线证据中已确认的本课起点档，向上看 1-2 档
2. 列出上一档/两档的核心架构决策点（控制流/能力/交互三域各找 1-2 个）
3. 每个决策点构造场景化题干（三句话：场景锚定 → 升级需求 → 问题抛出）
4. 设计 2 层追问（追问1 缩小到子决策，追问2 推向更极端场景）
5. 用 agent-reach 网页检索验证推演方向：搜 `{技术关键词} + "architecture evolution" / "scaling" / "production"`，找到至少 1 篇工业界讨论同问题的文章作为来源

#### 辅路径 A：架构演进文章 → 反向提炼（深度题来源）

执行步骤：
1. 用 agent-reach 网页检索搜本课核心技术 + "lessons learned" / "production journey" / "踩坑" / "从 0 到 1"
2. 信源优先级：一线公司技术博客 > Staff+ 工程师博客 > InfoQ/极客时间深度 > 高赞公众号
3. 新鲜度：≤ 2 年
4. 找作者"纠结过、试过多方案、最终选 X 因为 Y"的决策时刻
5. 反向成题：给出约束条件，问"如果你在当时位置怎么选"
6. 来源直接指向原文作为关联阅读

#### 调研通道（强制）

通道与降级说明见 `references/evolution-roadmap.md` §3.4，具体命令示例见 `references/interview-questions.md` §4.3。本阶段特有两条约束：

- **搜题用网页搜索、读原文用全文阅读**（别把搜索结果的摘要当原文用）。
- **禁止用通用 WebSearch 搜「XX 面试题」直接凑题**（出来的都是八股）。

#### 候选题卡片格式

每张卡片存入 `.course/{task_name}/phase-2/interview-candidates.md`：

```markdown
## 候选题 #N · {架构题/深度题}

**题目**：{场景化题干，2-4 句}

**追问链**：
- 追问 1：{具体子决策}
- 追问 2：{更极端场景或反直觉选择}

**质量维度检查**：
- [ ] 考察知识结构而非记忆
- [ ] 紧扣本课但超纲
- [ ] 有 trade-off

**来源依据**：{文章标题}（{URL}）
**建议入选**：是 / 否
```

#### 人工确认关卡

候选题全部产出后，**必须暂停等用户确认**：
- 将 8-10 张卡片呈现给用户
- 让用户选 4 道（可要求重拟某道、补充某方向、或调整配比）
- 用户确认的题目进入 Phase 3 终稿写作
- **禁止跳过此步骤直接写终稿**

## 案例/证据采集方向

- **课程类**：最有感觉、最能讲活、最能体现方法论价值的经历。
- **辅导类**：最能体现职级差、最能展示架构深度、最能回答面试官"为什么是你"的亮点成果。

## 证据使用判断表

| 用途 | 优先来源 |
|:---|:---|
| 情绪调动 / 个人亮点 / 讲述张力 | 经验线 (亲历/观察) |
| 模糊启发 / 讨论素材 | 经验线 或 事实线 |
| 确定性判断 / 架构标准 / 边界兜底 | 事实线 (公开/权威) |
| 架构演进佐证 / 工业案例 | 演进线 (agent-reach 调研, ≤1.5年) |

## 本阶段产出（必须）

- `主讲述线/经验卡`
- `事实支撑线/论据表`
- `证据分工表`（哪个负责张力，哪个负责证明）
- `证据边界说明`（哪些是个人见解，哪些是公认事实）
- `决策/架构理由卡`（若涉及关键技术选型或架构决策）
- `演进线/工业案例证据卡`（系列实战课，含新鲜度自检表）
- `深入思考题候选题卡片`（实战课默认包含，8-10 张，存 `interview-candidates.md`；需等用户确认后进入 Phase 3）

> 以上文件存入 `.course/{task_name}/phase-2/`。
