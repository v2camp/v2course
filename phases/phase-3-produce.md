# Phase 3 — Produce Core Assets（产出核心产物）

## 目标

在方向、主轴和证据系统明确后，按链式生产关系产出**本课型的核心产物**。每个产物只服务一个角色，确保表达风格稳定、不摇摆。

| 课型 | 生产链 |
|:---|:---|
| **公开课 / 录播课** | 3A 大纲 → 3B 讲义 → 3C 课程文档 |
| **实战课**（基础/实战、应用架构） | **跳过 3A** → 3B 讲义 → 3C 课程文档（二产物，无大纲） |

---

## 3A：产出大纲（结构层）

> **适用课型：公开课、录播课。实战课跳过本节** —— 实战课不产出大纲；
> 其骨架由 Phase 1 的主线结构直接提供，从 3B 讲义开始生产。

### 目标

把课程骨架搭清楚，运营拿到就能直接用来做流量物料。

### 输入

- Phase 1 主线结构
- Phase 2 证据卡（案例、数据、论据）

### 产出

- `大纲.md`（存入项目目录根，参与 Phase 5 审计）
- 过程产物存入 `.course/{task_name}/phase-3/3A/`

### 大纲内容规范（按课型）

#### 公开课大纲

```
# 第N讲: 标题
## 0. 课程信息
   - 时长 / 目标受众 / 核心价值 / 一句话主张
## 1-N. 分段结构（每段含）
   - 时间段
   - 本段目标
   - 核心内容要点（3-5条）
   - 案例/数据支撑
## 附录: 案例来源清单（每条含 URL + 摘要 + 用于哪段）
```

七大段结构必须齐全：破题段 / 核心判断段 / 公开案例段 / 焦虑拆解段 / 课程地图段 / 行动清单段 / 结论收口段

#### 实战课结构骨架（Phase 1 确定，**不单独产出大纲**）

实战课**无大纲产物**。以下八段结构由 **Phase 1 主线结构**确定，直接作为 3B 讲义的骨架：

```
# 第N讲: 标题
> 系列:{课程名}(共X课时)/ 本讲:第N课时 / 时长
## 一、系列桥接/开场破题
## 二、核心判断（一句话主张 + 错误vs正确认知表 + 本讲解决/不解决）
## 三、认知模型/原理铺垫
## 四、主案例展开（多帧拆解表:帧/关键行为/阶段/核心要点）
## 五、原理抽象（核心架构/关键代码段）
## 六、架构启示与演进路线（系列课）或 能力全景图/三域地图（单节课）
## 七、收口:行动清单
## 八、转化承接（后续课时handoff表 + 课程产品承接）
## 附录 A：深入思考题清单（实战课默认4道，仅列题干+分类，不展开）
## 附录 B：关键来源（链接+类型+发布时间）
```

#### 录播课大纲

```
# 课程名
> 总时长 / 章节数 / 目标受众 / 合作平台
## 章节列表（每章含）
   - 序号 + 标题
   - 时长（8-20min）
   - 核心知识点（3-5条）
   - 核心案例/演示
## 章节间衔接逻辑（上一章收尾→下一章钩子）
## 附录:参考来源
```

### 大纲禁用内容（全部移至讲义；仅适用于公开课/录播课）

大纲只讲"讲什么"和"为什么讲"，绝对不出现以下讲师专属内容：
- ❌ 讲师动作、演示动作、操作步骤
- ❌ 口播要点、话术提示、逐字稿
- ❌ 讲课节奏、互动设计、挖坑/填坑提示
- ❌ 【敲黑板】、【知识点】等干货标注（这些是讲课层面的事）

### 3A 退出门禁（仅适用于公开课/录播课）

- [ ] **结构完整度**：章节/分段无遗漏，逻辑连贯，与 Phase 1 主线一致
- [ ] **信息密度**：每个分段/章节有明确的核心内容要点，不是空标题
- [ ] **运营可用度**：运营拿到就能写文案、做海报、做详情页，不需要再问讲师"这节课讲什么"
- [ ] **无讲师内容残留**：大纲中没有讲师动作、口播要点等讲师专属内容

## 3B：产出讲义（讲师层）

### 目标

讲师拿到就能备课、上课的完整底稿。

### 前置条件

- **公开课 / 录播课**：3A 大纲已通过评审（结构确认、运营可用度达标）。
- **实战课**：Phase 1 主线结构已确定（无 3A 环节）。
- **（含代码的课）代码对照先行**：动笔前按 `references/multi-track-production.md` **§2.5** 做一轮「文档 ↔ 代码」对照——取**生效值**（四层）＋ 核**接线**（有没有调用点），把结论记入 `.course/{task_name}/phase-3/3B/code-alignment.md`（**出门禁见「3B 退出门禁」的"代码对照已闭环"一条**）。
  > **代码里写着什么，不等于运行时在用着什么。**先把参数与链路对齐，再落笔——否则整篇讲义会建在过期参数上（实测：同一组课程一次性查出 9~22 处这类偏差）。

### 输入

- **公开课 / 录播课**：`大纲.md`
- **实战课**：Phase 1 主线结构（无大纲，直接以此为骨架）
- Phase 2 完整证据（案例卡/代码论据/演进路线素材）
- （实战课）Demo 代码项目

### 产出

- `讲义.md`（存入项目目录根，参与 Phase 5 审计）
- `images/` 目录（图，由 archsvg 渲染的 SVG 存入，详见 `references/diagram-integration.md`）
- 过程产物存入 `.course/{task_name}/phase-3/3B/`

### 讲义内容规范

结构与上游骨架 **1:1 对应**（公开课/录播课以大纲为上游，**实战课以 Phase 1 主线结构为上游**），
并在其上增加讲师授课所需的全部内容：

| 内容维度 | 说明 |
|:---|:---|
| **完整口播内容** | 工程口语化、有张力、去 AI 腔，讲师拿着基本就能讲 |
| **演示动作/步骤** | live coding 步骤、控制台操作、界面切换提示 |
| **干货标注** | 【要点】、【知识点】、【敲黑板】承载核心干货 |
| **图引用** | 架构图/流程图/序列图（architecture/flow/sequence，由 archsvg 渲染，存 `images/`） |
| **【备课参考】** | 每节末尾 2-3 篇延展阅读，附价值说明 |
| **代码讲解** | （实战课）代码片段 + 逐行讲解 + 运行效果预期 |
| **画面提示** | （录播课）每段对应画面内容、出镜/屏幕操作说明 |
| **教学钩子** | 挖坑/填坑标注（仅讲师可见的教学节奏设计） |

#### 【备课参考】规范

每节末尾必须有 **【备课参考】** 区块，格式：

```
### 【备课参考】本节延展阅读

1. **{文章标题}** — {来源/作者}，{发布时间}
   - 价值：{一句话说明为什么值得读，能补充哪个知识点}
   - 链接：{URL}

2. **{文章标题}** — {来源/作者}，{发布时间}
   - 价值：{一句话说明为什么值得读，能补充哪个知识点}
   - 链接：{URL}
```

硬性要求：
- 每节至少 2 篇
- 必须是工业界真实来源（技术博客、官方文档、论文、大厂技术分享等）
- 价值说明要具体，不能写"值得一读"这种空话
- 标注发布时间，案例新鲜度原则上 ≤2 年

### 3B 核心写作与品质标准 (MANDATORY)

进入讲义生产阶段，必须强制遵循 `references/quality-guide.md` 指南。核心硬性门禁：

#### 1. 拟真口语表达（戒除 AI 腔）
详细规范见 `references/quality-guide.md §1`。
- **绝不动用 AI 过渡词**：严格封杀"首先/其次/综上所述"等学术教科书词汇，用工程口语替代。
- **资深技术 Leader 语气**：直接、生动、一针见血，使用工程师常用黑话与大白话。
- **张力讲课公式**：每个关键技术节点以"冲突场景/深夜窒息现场"驱动，**情绪张力必须完全依据用户给出的实际案例与工程事实，禁止凭空捏造虚假场景**；案例有缺时须在撰写前与用户商讨对齐。

#### 2. 扁平化深度干货输出（戒除夸大卡片包装）
详细规范见 `references/quality-guide.md §2`。
绝对禁用角色特化卡片，以高质量、中立且深度的通用技术干货形式直接呈现，使用平实工程词汇组织内容。
一律使用 **【要点】**、**【知识点】**、**【敲黑板】** 组织并高亮干货。

#### 3. 制图规范（走 archsvg，严禁 ASCII 图形）
详细规范见 `references/diagram-integration.md`（archsvg 调用约定）。
- 讲义中绝对禁止残留任何 ASCII 字符流程图
- 先写 IR JSON，经 `archsvg validate` 校验后 `archsvg render` 出独立 `.svg` 文件存放至 `images/`；禁止手写 SVG 坐标
- 配色与风格由 archsvg 统一（三域 role 配色），详见 `references/diagram-integration.md`

#### 4. 架构演进路线段写作规范（系列实战课）
当 Phase 1 决定本课包含"架构演进路线图"收口段时，必须遵循 `references/evolution-roadmap.md` 的四段式骨架。

#### 5. 应用架构课代码引用规范（飞书兼容）
仅适用于实战课·应用架构类型。详细规范见 `references/code-reference-feishu.md`。
- 双锚点法引用代码（类名 + 包路径简写）
- 代码片段标注路径注释
- 每讲必配核心代码索引表

#### 6. 附录深入思考题写作规范（实战课）
方法论与质量标准见 `references/interview-questions.md`。
当 Phase 1 决定本课包含"附录深入思考题"、且 Phase 2 用户已确认 4 道候选题后，在讲义末尾产出附录。

### 3B 退出门禁

- [ ] **与上游骨架 1:1 对应**：章节/分段完全对齐，不跑偏、不增删结构（公开课/录播课对大纲，实战课对 Phase 1 主线结构）
- [ ] **去 AI 腔合格**：无禁用词，口语化到位
- [ ] **图规范合格**：无 ASCII 图，archsvg 回执通过（showcase 15/15）、引用路径正确
- [ ] **【备课参考】达标**：每节至少 2 篇，有来源有价值说明
- [ ] **干货标注规范**：【要点】【知识点】【敲黑板】使用正确，无角色卡片
- [ ] **（实战课）代码可跑通**：代码示例与 Demo 一致
- [ ] **（含代码的课）代码对照已闭环**：`code-alignment.md` 已产出，且讲义里每个类名 / 常量 / 阈值都取过**生效值**、写成主链路的部件都核过**调用点**（判据见 `multi-track-production.md` §2.5）——这是"不许带着偏差出门"的闸门
- [ ] **（录播课）画面提示完整**：每段有对应画面说明
- [ ] **情绪张力有据可查**：所有痛点冲突场景基于真实案例

## 3C：产出课程文档（学员层）

### 目标

学员可以直接当教程读的技术文档。从讲义转换而来，但文体、视角、内容都做学员视角重构。

### 前置条件

3B 讲义已通过评审（内容完整、技术准确）。

### 输入

- 讲义.md
- `images/` 目录（复用）

### 产出

- `{课程名}.md`（无前缀，纯标题命名，存入项目目录根，参与 Phase 5 审计）
- 复用 `images/` 目录（不需要重新生成图，复用 archsvg 渲染产物；如需改动图，修改 IR 源而非重画）
- 过程产物存入 `.course/{task_name}/phase-3/3C/`

### 课程文档内容转换规则

结构与讲义 **1:1 对应**，但做以下维度的转换：

| 转换维度 | 讲义（讲师视角） | 课程文档（学员视角） |
|:---|:---|:---|
| **人称** | "咱先看"、"我给大家演示一下"、"大家注意" | "本节介绍"、"以下示例展示"、"需要注意的是" |
| **干货标注** | 【敲黑板】、【知识点】、【要点】 | 保留【知识点】、【要点】；【敲黑板】转为"注意"或"常见问题"小节 |
| **讲课提示** | 演示动作、互动设计、节奏提示、操作步骤描述 | 全部移除 |
| **备课参考** | 【备课参考】（讲师读的延展阅读） | 转为【延伸阅读】（筛选后保留对学员有价值的内容） |
| **情绪张力** | 痛点冲突、窒息现场、戏剧化表达、"深夜线上事故"等 | 保留问题场景和动机，但表达方式转为客观技术描述 |
| **代码讲解** | 逐行口播式讲解、"咱来看看这行代码" | 代码+注释式讲解，精简口播冗余，保留核心逻辑说明 |
| **挖坑/填坑** | 教学钩子标注 | 全部移除 |
| **附录思考题** | 完整的答题骨架（核心思路/关键权衡/延伸方向） | 保留题干和追问，移除答题骨架（只留问题，不给参考思路） |

### 课程文档文体规范

详细规范见 `references/quality-guide.md §4`。核心原则：

1. **客观中立**：不使用第一人称复数（"我们"、"咱"），不使用直接呼语（"大家"、"同学们"）
2. **书面技术语**：表达准确、专业、流畅，不是简单地把"咱"换成"我们"
3. **可独立阅读**：不依赖讲课语境、不假设读者听过前面的课（但可以有"详见第X节"的内部引用）
4. **知识密度高**：去掉口播冗余、互动环节、重复强调，保留纯粹的知识和技术内容
5. **结构清晰**：章节标题层级分明，读者可以快速定位和检索

#### 架构类课程文档的高阶文体要求

当课程类型为**实战课·应用架构**、或产物为**架构案例分析书**时，课程文档的写作除满足上述基本规范外，还应遵循 `references/architecture-case-writing.md` 的高阶规范：

- 风格基准为李智慧《大型网站技术架构》——平实直白、业务驱动、演进视角、全局权衡
- 每章遵循"技术挑战 → 应对策略 → 架构设计 → 治理兜底 → 小结"的五段式结构
- 核心结论配体感数字，方案对比用表格呈现，小结提炼设计原则而非复述内容
- 主动讲方案的局限性和兜底手段，体现架构 trade-off 思维

> 注意：`architecture-case-writing.md` 是 **高阶补充**，不替代 `quality-guide.md`。所有课程文档必须先满足 quality-guide 的底线要求，架构类内容在此基础上进一步提升写作质感。

### 3C 退出门禁

- [ ] **与讲义结构 1:1 对应**：章节/分段完全对齐
- [ ] **去口语彻底**：无"咱"、"大家"、"我们来看"、"敲黑板"等讲师口语残留
- [ ] **去教学残留**：无演示动作、无挖坑填坑、无互动提示、无讲师侧记
- [ ] **技术表达准确**：去口语后技术含义没有偏差、没有丢失关键信息
- [ ] **可独立阅读**：不依赖讲课语境，学员直接读能理解完整逻辑
- [ ] **【延伸阅读】质量**：从备课参考中筛选后保留的内容对学员有价值
- [ ] **（实战课）代码正确**：代码片段与讲义一致，注释清晰

## 3D：多版本转换/复制（可选生产路径）

### 适用场景

已有一个版本的完整产物（如 TS 版讲义 + 课程文档），需要产出另一技术栈版本（如 Java 版）。此时可跳过 3A/3B/3C 的从零创作，走"技术叶节点替换"式转换。

### 核心原则

1. **概念主轴 1:1 保留**：课程结构、章节顺序、干货标注位置、挖坑钩子、演进档位、核心判断必须与源版完全一致——这是"同一门课的另一个版本"，不是新课。
2. **技术栈求地道不翻译**：框架选型、类名、API 写法、状态管理机制遵循目标栈最地道的工程实践，禁止做"另一个技术栈的翻译腔"（即 Phase 4 L4 精神前置到转换动作里）。
3. **双轨独立、互不侵入**：转换产物不得出现任何"与 X 版相比 / X 版用 Y / 双轨"等跨版本对比表述，两个版本各自独立成篇。

### 转换子代理（推荐派发）

大体量（单文件 > 50KB）文件转换，建议派发**转换子代理**并行处理，每个版本/文件一个子代理。派发时**必须携带**以下强制约束 prompt（缺一不可，否则转换结果不可信）：

```
【约束】
1. 技术叶节点替换：仅替换技术栈层（框架类名/API/依赖/代码写法/配置），
   课程结构、章节标题、顺序、干货标注位置、挖坑填坑钩子、具备参考思路、
   情绪张力的驱动场景全部保留不删改。
2. 求地道不求翻译：Java 栈（如 Spring AI）就写最地道的实现，不做逐行 TS→Java 映射。
3. 双轨独立：全稿禁止出现"另一个版本/与TS版相比/双轨"等对比性表述与技术名词。
4. 结构保全：正文段落数、小节编号、附录清单（A/B/C…）与源版一致，不得遗漏附录。
5. 红线自检：转换完自查——目标栈禁用词（含源栈品牌名、API名）为 0，
```
