## 核心写作与品质标准 (MANDATORY)

进入核心产物生产阶段，必须强制遵循 `references/quality-guide.md` 指南。以下为核心写作硬性门禁：

### 1. 拟真口语表达（戒除 AI 腔）
- **绝不动用 AI 过渡词**：严格封杀"首先/其次/综上所述/具有里程碑意义/值得注意的是"等学术教科书词汇。
- **资深技术 Leader 语气**：说话要直接、生动、一针见血。使用工程师常用黑话与大白话（如"平趟"、"踩坑"、"背锅"、"防抖"、"物理级隔离"、"生产环境秒级吞吐"）。
- **张力讲课公式**：对每个关键技术节点的引入，遵循"冲突场景/深夜窒息现场"驱动。**情绪张力调动必须完全依据用户给出的实际案例与工程事实，绝对禁止凭空捏造虚假场景。** 若案例有缺，需在撰写前与用户商讨对齐。

### 2. 扁平化深度干货输出（戒除夸大卡片包装）
绝对禁用并彻底删除任何角色特化卡片，不针对特定角色单独提示，而是以高质量、中立且深度的通用技术干货形式直接呈现。一律使用平实工程词汇组织内容（详见 `references/quality-guide.md`）：
- **禁用卡片组件**：严禁使用 `💡 [讲师侧记]`、`⚠️ [学员踩坑警告]`、`🎯 [面试突围金句]` 等包装框。
- **中立词汇组织**：一律使用 **【要点】**、**【知识点】**、**【敲黑板】** 组织并高亮干货。
- **严禁浮夸绝对词汇**：严禁使用"闭眼背诵"、"职级差回答"、"神级话术"、"降维打击"等针对特定角色的浮夸或绝对化暗示词，专注客观深度和工程实践本质。

### 3. SVG 矢量图形设计（严禁 ASCII 图形）
- **绝对隔离**：讲义中绝对禁止残留任何 ASCII 字符流程图（如 `┌─┐` 或 `-->`）。
- **独立 SVG**：必须针对流程、架构、对比画出高精美的 SVG 矢量图，保存为独立 `.svg` 文件存放至对应课程目录下的 `images/` 子文件夹。
- **规范设计**：设计风格遵循现代化扁平科技感，采用三域通用配色体系（控制流域紫色系、能力域绿色系、交互域蓝色系），并使用标准的 Markdown 语法进行相对路径引用。

### 4. 架构演进路线段写作规范（系列实战课）
当 Phase 1 决定本课包含"架构演进路线图"收口段时，必须遵循 `references/evolution-roadmap.md` 的四段式骨架，约 10 分钟：

**X.1 当前坐标（2min）**：
- 【知识点】三域地图，定位本课实现的架构在三域中覆盖了什么
- 表格：手写实现 vs 框架实现的三域映射
- 与前序课程的能力进阶对照
- 收束句：这只是演进的起点

**X.2 为什么只是起点（2min）**：
- 3 类失败模式表格（表现 / 根因 / 由哪档解决），失败模式必须基于本课主 Demo 实际短板推导
- 【敲黑板】：架构瓶颈，调参解决不了

**X.3 演进路线图（5min）**：
按 S0→S4 顺序（起点档可合并），每档包含：
- SVG 架构图引用（每档至少 1 张，总图 evolution-roadmap.svg 必有）
- 核心变化（一句话）
- 解决什么（对应 X.2 哪个失败模式）
- 工业案例佐证（≤1.5 年，附来源链接 + 发布时间 + 量化指标）
- 关键工程要点（3-4 条可复用经验）
- 本质金句（一句话收束本档）
- 【敲黑板】（仅关键档位，标出代价/边界，如多 Worker 并行的 Token/资源成本）

**X.4 收口矩阵（1min）**：
- 三域 × 各档位演进矩阵表格
- 一句话定位本课落点
- 后续课程 handoff（下节课落地哪一档）

硬性规则：
- 起点档必须 = 本课主 Demo 实际实现的架构（严禁硬套通用模板）
- 每档工业案例必须标注来源 + 发布时间 + 量化数据出处
- SVG 总图必出（evolution-roadmap.svg），档位图按需出
- 引用外部企业架构图必须附 attribution（公司名 + 博客标题 + URL）

### 5. 应用架构课代码引用规范（飞书兼容）
> **仅适用于实战课·应用架构类型**。基础/实战课不涉及此规范。详细规则见 `references/architecture-course.md` 第四节。

应用架构课基于已有生产级代码讲解，文档最终发布到飞书（docs.feishu.cn），本地 `file://` 链接会全部失效。因此必须使用飞书兼容的代码引用方式。

#### 5.1 正文引用：双锚点法

正文中引用代码时，使用「**类名 + 包路径简写**」双锚点：

**格式**：`` `ClassName`（`package.subpackage`）``

- 类名用行内代码格式——学员可直接在 IDE 里搜类名（Cmd+O / Shift+Shift）
- 括号内是包路径简写——帮助定位模块位置

**示例**：
> 项目里用 `{ClassName}`（`{module.submodule}`）作为{模块功能描述}。

**规则**：
- 每个类**首次出现**时，必须给出类名 + 包路径简写
- **后续再次出现**同一类时，可只写类名，不用重复包路径
- 包路径简写从模块特征包开始，省略组织/项目通用前缀（如 `com.{company}.{project}`）
- 简写后必须能唯一识别到包，不能歧义
- **绝对禁止使用 `file://` 链接或本地绝对路径链接**

#### 5.2 代码片段标注

展示关键代码片段时，代码块第一行用注释标注相对路径：

```java
// 文件：{path/to/ClassName}.java
public class {ClassName} {
    // 核心逻辑
}
```

- 路径从 `src/main/java/`（或对应源目录）开始
- 只展示 10-30 行核心逻辑，省略部分用注释说明
- 完整代码让学员去 IDE 看，讲义不做代码搬运工

#### 5.3 每讲必配：核心代码索引表

每讲**末尾必须**有一张「**本讲核心代码索引**」表格：

| 模块 | 类名 | 相对路径 | 核心职责 |
|:---|:---|:---|:---|
| {模块A} | `{ClassA}` | `{path/to/ClassA}.java` | {一句话描述核心职责} |
| {模块B} | `{ClassB}` | `{path/to/ClassB}.java` | {一句话描述核心职责} |

要求：
- 列出本讲所有在正文中提到的类
- 按模块分组，同类模块放一起
- 核心职责一句话（≤20字）
- 类名、路径必须与真实代码 100% 一致

#### 5.4 系列课首讲前置说明

应用架构系列课的**第一节课开头**，必须在课程信息区标注：

```
> 教学代码根目录：`{path/to/project-root/}`
> 代码路径约定：所有相对路径均相对于 `{src/main/java/ 或对应源目录}`
> 建议学习方式：在 IDE 中打开项目，按类名搜索（Cmd+O / Shift+Shift）定位
```

### 6. 附录深入思考题写作规范（实战课）
当 Phase 1 决定本课包含"附录深入思考题"、且 Phase 2 用户已确认 4 道候选题后，必须遵循 `references/interview-questions.md` 的格式规范，在讲义末尾产出附录：

**前置条件**：Phase 2 用户已从 8-10 道候选题中选定 4 道（默认 3 架构题 + 1 深度题）。

**附录位置**：讲义正文最后（参考文献/拓展阅读之后，或作为独立附录章节）。

**每道题的标准结构**：

```markdown
### A.N {题目标题}（架构题/深度题）

{场景化题干，2-4 句，必须锚定本课 Demo 具体元素}

**追问 1**：{具体子决策问题}
**追问 2**：{更极端场景或反直觉选择}

**【答题骨架】**

- **核心思路**：{2-3 句话说清大方向，不展开细节}
- **关键权衡**：
  - {trade-off 1}：{一句话说明矛盾双方}
  - {trade-off 2}：{一句话说明矛盾双方}
- **延伸方向**：{1-2 个可以再深入的点，点到为止}

**【关联阅读】**
- [{文章标题}]({URL})
```

**附录引言**（固定文案，放在所有题目之前）：
> 以下问题不附标准答案，旨在锻炼架构思维与决策能力。建议在完成本课代码实践后，先自行组织答案框架，再结合"答题骨架"对比思路差异。

硬性规则：
- **篇幅控制**：4 道题总篇幅 ≤ 讲义总篇幅 15%
- **不给完整答案**：只给答题骨架，不给逐字标准答案
- **追问链 2 层**：层层深入，不是平行问题
- **关联阅读必填**：每道题至少 1 条工业界真实来源
- **场景锚定**：题干必须提到本课 Demo 具体元素（模块名/架构形态），禁止泛题
- **类型标签**：每道题标注（架构题）或（深度题）
- **配比**：默认 3 架构 + 1 深度
- **答题骨架三层必齐**：核心思路 + 关键权衡 + 延伸方向
